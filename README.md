# 센터 매출 관리 (gym-ops)

호석님(지점장)의 헬스장 1개 지점 운영을 위한 회원·매출·업무 관리 웹앱입니다.
**이 문서는 대화 기록이 사라져도 새로운 Claude 세션이 이 프로젝트를 곧바로 이어받을 수 있도록 만든 인수인계 문서입니다.**
새 세션에서 이어서 개발할 때는, 이 폴더(zip을 풀어놓은 것) 전체를 업로드하고 "이 프로젝트 README부터 읽고 이어서 개발해줘"라고 요청하면 됩니다.

## 이게 뭔가요

- 프론트엔드: 빌드 과정 없는 순수 HTML/CSS/JS (프레임워크·번들러 없음)
- 백엔드: Supabase (Postgres + Auth + REST API). SDK를 설치하지 않고 `fetch()`로 REST API(PostgREST)를 직접 호출합니다.
- 배포: Vercel 프로젝트가 **GitHub 저장소(gym-ops)와 연동**되어 있고, 그 저장소의 `main` 브랜치가 바뀌면 Vercel이 자동 배포함(2026-09-03에 실제 Vercel 프로덕션 배포 화면에서 "Source: main / Add files via upload"로 확인됨 — 이전에는 "git 연동 아님"으로 잘못 적혀 있었음, 바로 아래 배포 방법 참고). 별도 로컬 git이나 커밋 명령 없이, **GitHub 저장소 페이지에서 파일을 웹으로 업로드**해서 커밋하는 방식으로 배포함. 코드를 고칠 때마다 새 파일들을 만들어 GitHub에 업로드해야 반영됩니다.
- 권한: Supabase RLS(Row Level Security)로 지점장/트레이너 권한을 서버(DB)단에서 강제합니다. `is_manager()` 함수로 지점장 여부를 판별.

| `index.html`, `login.html`, `signup.html` | 로그인/회원가입 |
| `home.html` | 로그인 직후 첫 화면. 자주 쓰는 메뉴 아이콘 + 지점장 전용 "데이터 백업" 버튼 |

| `migration_2~31_*.sql` | 이후 추가된 기능들의 마이그레이션. **번호 순서대로 전부 실행되어 있어야** 코드가 정상 동작함 |

## 지금까지 구현된 주요 기능

- 로그인/회원가입, 지점장·트레이너 권한 분리 (RLS)
- **트레이너 화면 구성** (2026-09-02 최신): 트레이너로 로그인하면 상단 메뉴에 홈/회원 관리/센터 매출/PT 관리/PT 스케줄/업무 리스트/미팅 기록만 보이고, 대시보드·매출 입력·만료회원 · TM·이용권 관리·직원 관리는 메뉴에서 숨겨짐. 지점장은 그대로 전체 메뉴가 다 보임. `auth.js`의 `applyRoleNav()` 함수(트레이너일 때 숨길 href 목록 하나만 관리)로 모든 페이지에 공통 적용되므로, 나중에 트레이너에게 보여줄 메뉴가 또 바뀌면 이 함수의 `hideHrefs` 배열 하나만 고치면 됨
- 회원 관리: 검색, 등록/수정/삭제, 엑셀 일괄 업로드(기존 타 프로그램 양식 자동 인식 + 간단 양식). 트레이너도 전체 회원을 조회하고 신규 회원을 직접 등록할 수 있음(담당 트레이너는 본인으로 고정). 단, 엑셀 일괄 업로드·회원 삭제·담당 트레이너 재배정은 지점장 전용으로 유지
- 이용권 판매: 비플 참고한 장바구니 방식 (종류선택 → 담기 → 결제(담당자/결제수단/날짜별 상세설정) → 등록)
- 이용권 상품(가격표) 관리 (지점장 전용)
- 매출 입력/조회/삭제, 결제수단 기록
- 만료 예정·만료 회원 TM(연락) 관리, 카테고리별 필터
- 업무 리스트 (담당자 지정, 반복 업무, 완료 체크)
- 대시보드: 만료 임박 현황, 재등록 확률, 일간/주간/월간 매출 보고(총매출/FC매출/PT총매출 카드), 상품별 재등록 현황
- 만료회원·TM 페이지에도 대시보드와 동일한 "헬스이용권·그룹PT 만료 임박 인원 / 이번 달 재등록 확률" 요약 카드 표시 (카드를 누르면 목록이 해당 상품으로 필터됨)

`data.js`에 `saleDisplayItemName(sale)` 공용 함수를 새로 만들어서 두 화면(대시보드·센터 매출)이 똑같은 기준으로 종목명을 뽑도록 통일함: ① 상품이 연결된 매출이면 그 상품 이름 그대로, ② 상품 연결은 없어도 POS 판매내역 엑셀로 가져온 매출이면(사용자가 방금 대량으로 가져온 8월 매출들이 여기 해당) 그때 메모에 남겨둔 원본 상품명("헬스이용권 6개월", "락커 3개월", "프리미엄 1:1 PT 40회 5개월" 등)을 정리해서 보여줌(지점명·"(FC)/(PT)" 태그·"외 N건"·"(환불)" 같은 군더더기는 지우고 상품명만 남김), ③ 그것도 없으면 마지막으로 카테고리 이름을 보여줌. 6가지 케이스(상품 연결/POS가져오기 단일상품/카테고리 폴백/POS가져오기 묶음+환불/POS가져오기 PT/POS가져오기 일일권)로 정확히 기대한 이름이 나오는지 확인했고, 기존 센터 매출 화면의 정산표 결과가 하나도 안 바뀌었는지(회귀 테스트)도 재확인함.

## 새 기능: POS "판매내역" 엑셀 일괄 가져오기 (2026-09-01)

지점장님이 실제 POS(결제 단말기) 프로그램에서 뽑은 "8월 총 매출" 원본 엑셀을 기존 "엑셀로 회원 일괄 등록"에 넣었더니 전부 건너뛰어지는 문제를 겪음. 확인해보니 그 파일은 원래 이 업로더가 기대하던 "회원별 현재 이용권 현황(만료일 포함)" 형식이 아니라, "이번 달 결제 건별 거래 로그"(결제일시·회원명·연락처·판매상품·결제금액 등 컬럼이 있는, 만료일은 아예 없는 형식)였음. 사용자에게 원하는 게 뭔지 확인한 결과(① 이 매출들을 앱에 과거 기록으로 채워넣기, ② 회원 현재 상태도 같이 최신화, 둘 다 원함) 이 형식 전용의 새 가져오기 기능을 만듦.

**동작 방식**: 업로드 화면(`members.html`)이 헤더에 `결제일시`·`판매상품`·`회원명` 컬럼이 있으면 이 형식으로 자동 인식(`detectSheet()`에 `pos_sales` 모드 추가). 행마다: ① 전화번호로 회원을 찾아 없으면 새로 등록, ② 결제분류가 "결제"·"미수금"이면 결제금액을(분할결제여도 그 거래에서 실제 걷힌 금액이라 정확함), "환불"이면 환불지급액을(이미 음수) 매출 금액으로 그대로 등록, ③ 판매상품 텍스트("(평산)(FC) 헬스이용권 12개월", "(평산)(PT) 1:1 PT 20회" 등)를 분석해서 회원권/PT/그룹PT/락커/운동복/일일권 중 하나로 자동 분류, ④ 신규/재등록은 "이번 가져오기에서 새로 만든 회원의 그 항목 첫 구매만 신규, 나머지는 재등록"으로 판단(분할결제로 같은 판매번호가 두 번 나오는 건 같은 취급으로 묶어서 처리), ⑤ 판매담당자 이름을 직원 목록과 매칭해서 담당자로 기록, ⑥ 회원의 현재 이용권 만료일(구매일 + 이용기간)과 개인PT 잔여횟수도 같이 업데이트.

**여러 상품이 한 번에 묶여 결제된 건("헬스이용권 12개월 외 2건" 등)**: 항목별 금액이 안 쪼개져 있어서 자신있게 분류할 수 없음 — 사용자 확인 후, 건너뛰지 않고 전부 "미분류(확인필요)" 카테고리(`sales.category`에 신설, `migration_33_sales_uncategorized.sql`)로 매출은 등록해서 총액은 처음부터 정확하게 잡히도록 하고, 회원 현재 상태 업데이트는 항목을 특정할 수 없어 건너뜀. 매출 입력 화면에서 나중에 항목만 직접 재분류하면 됨 (센터 매출의 "기타" 항목·정산표에도 "미분류"가 함께 표시되도록 반영함).

**환불·미수금 처리**(사용자가 "앱 설계에 맞게 알아서" 처리해달라고 요청함): 미수금 상태 행도 결제금액이 실제로 채워져 있어서(그 시점까지 걷힌 금액) 일반 매출처럼 그대로 등록함 — 분할결제 진행 과정을 그대로 매출 이력으로 남기는 셈. 환불은 음수 금액의 매출 건으로 등록해서, 별도 로직 없이도 기존 합계 계산(센터 매출·대시보드 등은 전부 매출 금액을 그냥 더하는 방식이라)에서 자동으로 총매출이 정확히 줄어들게 함.

**알려진 한계**(README에 명시): PT 잔여횟수는 "더하기"가 아니라 "그 구매 건의 횟수로 덮어쓰기"라서, 어떤 회원이 이전에 남은 세션이 있는 상태에서 세션을 추가로 구매한 경우라면 실제 잔여횟수보다 적게 잡힐 수 있음(이번에 실제 업로드해본 8월 파일에는 이런 경우가 없었음 - 필요하면 PT 관리에서 수동으로 잔여횟수를 다시 맞추면 됨). 분할결제 건의 이용권 만료일은 "구매일+기간"을 매 건마다 다시 계산해서 덮어쓰는 방식이라, 마지막(가장 늦은 날짜의) 분할건 기준으로 만료일이 계산됨(며칠 정도 차이만 남).

**검증**: 실제로 사용자가 올리려 했던 "8월 총 매출 평산점.xlsx"(260건, 결제 243·미수금 15·환불 2)를 그대로 넣어서 Playwright로 전량 처리를 확인함 — 신규회원 175명 생성, 매출 260건 전부 등록(스킵/오류 0건), 카테고리 합계가 정확히 260건으로 맞아떨어짐, 분할결제 사례(김광목: 100,000원+299,000원=399,000원, 둘 다 신규 회원권으로 일관되게 태깅됨) 검증, 프리미엄 PT(40회/5개월) 구매 건이 PT 잔여횟수 40·PT만료일을 정확히 반영하는지 확인, 환불 2건이 정확히 음수 금액·재등록 카테고리로 등록되는지 확인, 묶음결제 건이 미분류로 빠짐없이 등록되는지 확인.

**출시 직후 실제 사용 중 발견된 버그(2026-09-01, 같은 날 수정)**: 사용자가 실제로 이 파일을 업로드했더니 "매출 0건 등록(신규 회원 19명 포함) · 건너뜀 260건"으로 나와서 매출이 하나도 안 들어감. 원인은 엑셀을 `{ raw: false }`로 읽어서(날짜 컬럼 서식을 살리려고 기존부터 이렇게 읽고 있었음) "결제금액"·"환불지급액"처럼 천단위 콤마 서식(`#,##0`)이 걸린 숫자 셀이 `399000`이 아니라 `"399,000"`이라는 문자열로 들어왔고, 여기에 그냥 `Number()`를 쓰면 콤마 때문에 `NaN`이 되어 모든 행이 "금액 인식 실패"로 건너뛰어졌던 것. 회원은 매출 확인보다 먼저 만들어지는 순서라 회원 19명만 먼저 생성되고 그 뒤 매출 등록 단계에서 전부 실패한 것으로 보임. 콤마·"원" 등을 제거하고 숫자만 남겨서 변환하는 `numFromFormatted()` 헬퍼를 새로 만들어 이 두 필드에 적용해서 고침 (실제로 콤마가 섞인 값으로 다시 재현 테스트해서, 고치기 전엔 100% 재현되고 고친 후엔 정상 동작하는 것까지 확인함). 겸사겸사 업로드 처리 중(몇 분씩 걸릴 수 있음) 버튼을 다시 누르면 같은 업로드가 두 번 겹쳐 돌면서 회원이 중복 생성될 수 있는 위험도 있어서, 처리 중엔 "업로드 시작" 버튼이 비활성화되도록 안전장치를 추가함. 이미 이 버그 상태로 생성된 회원(이름·전화번호만 있고 매출/현재상태는 비어있는 회원들)이 있어도 걱정 없음 — 이 가져오기는 전화번호 기준으로 있으면 그대로 쓰고 없으면 새로 만드는 방식이라, 고친 버전으로 같은 파일을 다시 올리면 중복 없이 이어서 채워짐.

## 버그 수정: 회원 삭제 시 외래키 오류 (2026-09-01)

**증상**: PT 회원 관리 자동 연동 기능을 실제로 써본 사용자가, 테스트로 등록했던 회원을 삭제하려다 `HTTP 409: update or delete on table "members" violates foreign key constraint "pt_care_logs_member_id_fkey"` 오류를 만남. `pt_care_logs`가 이 회원을 참조하고 있는데 그 연결을 안 끊고 회원을 바로 지우려고 해서 발생.

**원인**: 회원 삭제(`deleteMember()`, `data.js`)는 원래 그 회원에 걸린 `sales`(매출)·`tm_logs`(연락 기록)만 먼저 지우고 나서 회원을 지우도록 되어 있었음. 그런데 이번 세션에서 새로 추가된 `pt_care_logs`(PT 회원 관리 자동 연동) 테이블은 이 정리 로직에 반영이 안 되어 있었고, 점검해보니 같은 이유로 걸릴 수 있는 곳이 두 군데 더 있었음: `pt_bookings`(PT 스케줄 예약 기록)와 `pt_leads`(PT 리드가 이 회원으로 "등록전환"되며 남겨둔 연결)·`tasks`(업무에 회원이 태그된 경우).

**수정**: `deleteMember()`가 회원을 지우기 전에 순서대로 다음을 처리하도록 확장함 — ① `pt_leads`: 리드 자체(상담 이력)는 남기고 `converted_member_id`/`converted_sale_id` 연결만 해제, ② `pt_care_logs`·`pt_bookings`: 매출/연락 기록과 마찬가지로 이 회원의 기록이라 함께 삭제, ③ `tasks`: 업무 자체는 지우지 않고 회원 연결만 해제, ④ 기존대로 `tm_logs`·`sales` 삭제, ⑤ 마지막으로 회원 삭제. 회원 삭제 확인 문구에도 "PT 회원 관리/PT 스케줄 기록도 함께 삭제됨"을 추가함. Playwright로 이 순서(리드 연결 해제 → PT 관리·스케줄 삭제 → 업무 연결 해제 → 연락·매출 삭제 → 회원 삭제)가 정확히 지켜지고 최종적으로 오류 없이 삭제되는지 검증함. DB 스키마 변경은 없어서 새 마이그레이션 SQL은 필요 없음.

## 로딩 속도 · 안정성 (2026-08-31)

체감 렉/오류를 줄이려고 앱 전반을 손봤음:

- **서로 무관한 API 요청을 순차적으로 하나씩 기다리던 걸 동시에 보내도록 바꿈.** PT 관리(`pt.html`)는 초기 로딩에 프로필/직원목록/회원목록/상담기록/PT 회원 관리/미응답기록/목표까지 최대 7번을 차례로 기다렸었는데, 서로 의존관계 없는 요청들은 `Promise.allSettled`로 한꺼번에 보내도록 바꿔서 체감 로딩 시간이 크게 줄었음 (PT 스케줄 `schedule.html`도 동일하게 개선). 업무 리스트(`tasks.html`)는 담당자 목록(`fetchStaff`)을 두 군데서 중복 호출하던 것도 하나로 합침. 회원 관리(`members.html`)는 "회원 등록" 팝업용 트레이너 목록 조회가 정작 중요한 회원 표 로딩을 막고 있던 걸 풀어서, 회원 표가 트레이너 목록과 상관없이 먼저 뜨도록 함.
- **로그인한 사람 정보(`getMyProfile()`, `auth.js`)를 못 불러오면 화면 전체가 "로딩 중..."인 채로 영영 멈춰버리던 버그를 고침.** 모든 페이지가 맨 처음에 이 함수부터 호출하는데, 여기서 네트워크가 살짝 끊기기만 해도(와이파이 순간 끊김 등) 그 오류를 아무도 못 잡아서 페이지 초기화가 그 자리에서 조용히 멈췄음(사용자 입장에선 "PT 스케줄 화면이 텅 비어서 안 뜬다"처럼 보임). 이제는 실패해도 0.5초 후 자동으로 한 번 더 시도하고, 그래도 안 되면 예외를 던지지 않고 안전하게 넘어가도록 고쳐서, 새로고침 없이도 대부분 저절로 복구됨.
- 위 항목들은 Playwright로 지연 요청/네트워크 실패 상황을 흉내내서 검증함 (예: 요청마다 400ms 지연을 준 상태에서 PT 관리 초기 로딩이 병렬화 전 이론상 2.8초 → 병렬화 후 약 1.1초로 단축, 프로필 조회 첫 시도 실패 후 재시도로 정상 복구 등).
- **PT 관리(`pt.html`)의 "예상 매출" 카드가 지난 달 이전 리드까지 계속 끌어와서 매달 숫자가 잘못 잡히던 버그를 고침.** 주차별 매출 기록 표·재등록/OT 확정 조사·확정 매출 카드는 전부 "상담일 또는 OT일이 이번 달에 걸치는 리드만" 보는데, 예상 매출 카드만 날짜는 안 보고 상태(진행중 여부)만 보고 계산하고 있었음 — 그래서 몇 달 전에 남겨두고 상태를 안 정리한 리드가 있으면, 정작 이번 달 표에는 그 리드가 안 보이는데도 예상 매출에는 계속 잡혔음(트레이너 구분 없이 다 같은 버그). "이번 달에 속하는 리드" 판정을 `isLeadInMonth()` 공용 함수 하나로 합쳐서 표·카드·미니 요약이 전부 같은 기준을 쓰도록 고쳤고, 이제 예상 매출 카드를 눌러 이동하는 주차별 매출 기록 표와 카드 숫자가 항상 서로 맞음.

## 트레이너 입장으로 전체 앱 직접 사용해보며 점검 (2026-08-31)

사용자 요청으로, 트레이너 계정이 되었다고 가정하고 홈 → 대시보드 → 회원 관리 → PT 관리(3개 탭) → PT 스케줄(예약·출석 처리) → 업무 리스트 → 미팅 기록 → 직원 관리까지 실제 화면 흐름을 Playwright로 하나씩 눌러가며 점검함 (모든 페이지·테이블이 서로 연동된 가짜 데이터로 재현: 담당 회원 2명 중 1명은 잔여 12회, PT 예약 1건, 상담 리드 1건, 이미 연동된 PT 회원 관리 기록 1건, 업무 1건).

Playwright로 트레이너 계정으로 홈·대시보드 화면을 열어서 두 링크가 실제로 안 보이는지 재검증함.

OT 관리 탭에 상담만 하고 아직 OT 날짜를 안 잡은 리드가 안 보이는 건 "OT 날짜가 잡힌 사람만 보여준다"는 원래 설계대로였고 실제로는 버그가 아니었음(주차별 매출 기록 표에는 정상적으로 나타남, 값도 다 정확히 들어있는 걸 재확인).

## 상품 카테고리 "기타" 신설 + 양도비(30,000원) 등록 (2026-09-01)

"상품에서 기타 하나 만들어주고 기타 항목에 양도비(30,000원) 추가해줘" 요청. 지금까지 상품(이용권) 카테고리는 헬스이용권/그룹PT/개인PT/락커/운동복 5개뿐이었는데, 회원 만료일과 연결되지 않는 1회성 판매 상품(양도비처럼)을 담을 곳이 없었음.

- `PRODUCT_CATEGORY_TO_SALE_CATEGORY`에 `etc: 'etc'`를 추가해서, 회원 상세에서 "기타" 상품을 팔면 매출 항목도 정확히 "기타"로 기록되게 함 (안 해두면 기본값인 "회원권 재등록"으로 잘못 잡힘).
- `CATEGORY_LABEL`에 `etc: '기타'`, `CENTER_SALES_BUCKETS.etc` 배열에도 `'etc'`를 추가해서 센터 매출(`center-sales.html`) 정산표의 "기타" 열에도 자동으로 합산되게 함.
- `migration_34_products_etc_category.sql`에 "양도비" 상품(카테고리: 기타, 가격 30,000원, 기간/횟수 없음) INSERT문까지 포함해뒀음 — SQL만 실행하면 스키마 변경과 상품 등록이 한 번에 끝남.
- Playwright로 검증: 이용권 관리 화면에 "기타" 탭과 "양도비 · 30,000원"이 뜨는지, 회원 상세 모달의 "이용권 판매" 카테고리 탭에도 "기타"가 뜨고 양도비를 장바구니에 담아 결제 화면으로 넘어가면 "종료일/횟수"란에 (기간이 없는 상품이라) "기간 없음"이 정확히 표시되는지, 최종 등록 시 서버로 보내는 매출 데이터의 `category`가 실제로 `"etc"`로 찍히는지까지 확인함.

**배포 직후 발견/수정한 버그: 만료회원·TM 페이지 전체가 "HTTP 400: column members.null does not exist" 에러로 깨짐.** `fetchExpiringItems()`가 만료 예정 회원을 조회할 때 `EXPIRY_CATEGORIES`의 모든 항목을 돌면서 `{필드명}.lte.{날짜}` 형태로 Supabase 쿼리 조건을 자동으로 만드는데, 방금 추가한 "기타" 항목은 회원 만료일 컬럼이 없어서 `field`가 `null`이었고, 이게 그대로 문자열로 들어가 `null.lte.2026-...`라는, 존재하지 않는 "null"이라는 컬럼을 찾는 조건이 되어버렸음. PostgREST는 `or=(...)` 안의 조건 중 하나라도 존재하지 않는 컬럼이면 쿼리 전체를 400 에러로 거부하기 때문에, 기타 항목과 무관한 헬스이용권·그룹PT 만료 카드/표까지 전부 같이 깨졌던 것. `field`가 없는 카테고리는 애초에 만료 추적 대상이 아니므로 이 쿼리를 만들 때 걸러내도록 (`EXPIRY_CATEGORIES.filter(c => c.field)`) 고쳤고, 같은 이유로 회원 데이터를 순회하며 만료일을 읽는 루프에도 방어 코드를 추가함. Playwright로 재현 후 수정을 확인: 수정 전 재현 시 실제로 쿼리에 `null.lte`가 포함되며 400이 발생했고, 수정 후에는 쿼리에서 "기타"가 빠지고 페이지가 정상적으로 만료 예정 회원을 표시함.

## 매출 입력 화면 "최근 매출 내역"에 방금 등록한 개인PT가 안 보이던 문제 (2026-09-01)

"회원관리에서 개인PT 등록했던 이력은 왜 안 나와? 매출정산에는 다 맞게 나오던데" 라는 문의. 센터 매출(정산표)에는 정상적으로 잡히는 걸로 봐서 매출 데이터 자체(카테고리 등)는 정확히 저장되고 있었고, 문제는 매출 입력(`sales.html`) 화면의 "최근 매출 내역" 표시 쪽에 있었음.

- `fetchRecentSales()`가 최근 매출 15건을 가져올 때 `order=sale_date.desc`(날짜만) 기준으로 정렬 후 상위 15개만 잘랐는데, 하루에 매출이 15건 넘게 몰리면(오늘처럼) 같은 날짜 안에서의 순서는 보장되지 않아서, 방금 등록한 매출이 "15건 안"에 못 들고 밀려날 수 있었음 — 특히 여러 건을 몰아서 등록하는 날일수록 최근에 등록한 것부터 누락되기 쉬운 구조였음.
- `order=sale_date.desc,created_at.desc`로 등록 시각까지 2차 정렬 기준으로 추가해서, 날짜가 같으면 항상 "가장 최근에 등록한 순"으로 정렬되도록 고침. 이제 오늘 몇 건이 등록되든 방금 등록한 건이 항상 최상단 근처에 뜨고, 15건 제한에 밀려 안 보이는 일이 없음.
- Playwright로 재현·검증: 오늘 날짜로 16건을 만들고 그중 가장 나중에 만든 걸 "신규 PT"로 지정한 뒤, 실제 Supabase 정렬 로직(날짜→등록시각 순)을 흉내내서 확인한 결과 그 PT 건이 정상적으로 목록에 포함됨을 확인.

## 매출 입력 화면 "최근 매출 내역" 10건씩 페이지 넘김 추가 (2026-09-01)

"건수를 10개 넘어가면 다음 페이지로 넘어가게끔 구현해줘" 요청. 방금 15건→100건으로 넉넉히 불러오도록 고친 김에, 대시보드의 "최근 매출 내역"(5건씩 페이지네이션)과 똑같은 방식으로 매출 입력(`sales.html`) 표에도 페이지 넘김을 붙임.

- 서버에서 한 번에 최대 100건을 가져온 뒤(`fetchRecentSales(100)`), 화면에서 10건씩 잘라 보여주고 ◀/▶ 버튼과 "N / M" 페이지 표시로 넘기도록 함 (페이지 넘길 때마다 서버에 다시 요청하지 않음).
- 새 매출을 등록하면 자동으로 1페이지로 돌아가서, 방금 등록한 매출이 목록 맨 위(바로 위에서 고친 정렬 기준 덕분에 항상 최상단)에 바로 보이도록 함.
- Playwright로 23건짜리 매출로 재현: 1페이지 10건/2페이지 10건/3페이지 3건으로 정확히 나뉘고, 1페이지에서 이전 버튼·마지막 페이지에서 다음 버튼이 비활성화되는 것까지 확인. 매출을 새로 등록하면 1페이지로 리셋되어 등록한 금액이 목록 맨 위에 바로 뜨는 것도 확인함.

## 0원짜리 항목은 매출로 안 남도록 수정 (2026-09-01)

"0원된거는 입력 안해줘도 되는데 없애게끔 구현해줄 수 있어? 0원 잡은 것도 매출로 잡아놓더라" 요청. 락커/운동복처럼 이용권과 같이 끼워주고 따로 돈은 안 받는 항목을 회원 등록/이용권 판매 화면에서 상품만 고르고 금액을 비워두거나 0으로 두면, 회원의 만료일 등은 잘 반영되는데 그 옆에서 "0원짜리 매출"까지 같이 기록되고 있었음 — 그게 매출 입력 화면 "최근 매출 내역"에 실제 매출이 아닌 0원 줄들로 계속 쌓였던 것.

- **"+ 회원 등록"(신규 회원 등록 폼)**: 각 항목(이용권/그룹PT/개인PT/락커/운동복)의 금액이 0원으로 계산되면 그 항목만 매출 기록에서 제외하도록 고침. 회원의 이용권 종목·만료일·PT 잔여횟수 등은 매출 기록 여부와 무관하게 그대로 반영됨(원래도 회원 정보 저장과 매출 기록은 별개 단계였음). 0원 항목이 있으면 등록 완료 토스트에 "○○은 0원이라 매출에는 남기지 않았습니다"라고 안내함.
- **회원 상세 모달의 "이용권 판매(등록)" 장바구니**: 마찬가지로 담은 상품 중 금액이 0원인 것은 매출로 기록하지 않고, 회원 정보(만료일 등)만 반영함. 안내 문구도 동일하게 0원 항목을 알려줌.
- **주의해서 같이 고친 부분**: 개인PT를 담당 트레이너와 함께 등록하면 그 트레이너의 "PT 회원 관리" 탭에 자동으로 연동해주는 기능이 있는데, 이 연동 여부를 원래 "매출이 기록됐는지"로 판단하고 있어서 이번 수정 때문에 "0원 무료 체험 PT"를 등록하면 이 자동 연동이 깨질 뻔했음. 매출 기록 여부가 아니라 "개인PT 상품을 실제로 선택했는지"를 직접 보도록 고쳐서, 0원 PT를 등록해도 PT 회원 관리 자동 연동은 그대로 정상 작동하도록 함.
- Playwright로 검증: (1) 유료 헬스이용권(21만원) + 무료 락커(0원)를 동시에 신규 등록하면 매출은 헬스이용권 1건만 기록되고 락커의 만료일은 정상 반영됨. (2) 기존 회원 상세에서 유료 헬스이용권 + 금액을 0으로 바꾼 락커를 함께 판매해도 마찬가지로 매출 1건만 기록됨. (3) 담당 트레이너를 지정하고 0원 체험 PT를 등록해도 PT 회원 관리 탭 자동 연동은 그대로 동작함.

## 업무 리스트: 일일/요일별 주간/개인 업무로 묶어서 접었다 펼치게 개선 (2026-09-01)

"업무리스트 혹시 일자별, 주차별, 월별 이런식으로 묶음으로 나타내게해줘. 일일업무, 월요일 주간업무 등 해서 클릭하면 나오게끔 해줘도 되고." 요청. 마이크로소프트 투두 화면 캡처를 참고 이미지로 보내주셔서(실제로 그 앱처럼 만들어달라는 게 아니라 "이런 묶음+펼치기 스타일"을 참고하라는 의미로 확인), 업무 목록이 한 줄로 쭉 길게 나열되던 걸 반복 설정 기준으로 묶어서 보여주도록 `tasks.html`을 고침.

- 업무를 4가지로 자동 묶음: **일일 업무**(매일 반복) → **월~일 요일별 주간업무**(매주 반복, 해당 요일 것들끼리) → **개인 업무**(반복 없음, 마감일만 있는 낱개 업무). 업무가 하나도 없는 묶음(예: 아무도 화요일 주간업무를 안 만들었으면)은 아예 안 보여줌.
- 각 묶음은 제목 줄(예: "월요일 주간업무 · 1/2 완료")만 먼저 보이고, **그 줄을 클릭해야 안의 업무들이 펼쳐지는** 방식(▼/▲ 아이콘으로 표시) — 업무가 아무리 많아져도 목록 전체 길이가 늘어나지 않음.
- 처음 페이지를 열면 "일일 업무"·"오늘 요일에 해당하는 주간업무"·"개인 업무"는 자동으로 펼쳐진 상태로 시작하고(당장 오늘 봐야 할 것들), 그 외 요일 묶음은 접힌 채로 시작함. 이후엔 사용자가 누른 대로(펼침/접음) 그대로 유지됨.
- 완료 처리한 업무는 마이크로소프트 투두처럼 그 묶음 목록 안에 취소선으로 표시된 채 계속 보임(맨 위엔 아직 안 한 것, 아래로 완료된 것). 예전처럼 화면 하단에 "완료됨 N" 접이식 섹션을 따로 두는 방식은 없앰 - 묶음별로 몇 개 중 몇 개를 했는지 바로 보이는 게 더 명확해서 이렇게 바꿈.
- 예전에 있던 "미완료 업무 15개씩 페이지 넘김"은 이제 묶음 접기/펼치기가 그 역할을 대신하므로 제거함.
- Playwright로 검증: 요일별로 섞인 업무 8개를 넣고 묶음 순서(일일→오늘요일→다른요일→개인)와 개수 표시가 정확한지, 기본 펼침 상태(오늘 요일 것만 펼쳐지고 다른 요일은 접힘)가 맞는지, 접힌 묶음을 클릭하면 펼쳐지는지, 체크박스로 완료 처리하면 그 묶음의 "N/M 완료" 숫자가 바로 갱신되는지까지 확인함. 스크린샷으로도 실제 화면 모습을 직접 확인함.

## 업무 리스트 반복 설정에 "매월" 추가 (2026-09-02)

"반복업무가 일, 주 밖에 없는데 월도 하나 만들어줘, 월간업무도 하나 넣을 거라" 요청. 그 전까지는 업무 제목에 "매월 마지막 주 수요일 ..."처럼 직접 텍스트로 적어 넣는 임시방편을 쓰고 계셨음(업무 추가 폼에는 반복없음/매일/매주만 있었음) — 이번에 "매월" 자체를 정식 반복 옵션으로 추가함.

- **데이터 모델**: `tasks.repeat_type`에 `monthly`를 추가하고, "몇째 주"를 나타내는 새 컬럼 `repeat_week_ordinal`(1~4 = 첫째~넷째 주, -1 = 마지막 주)을 만듦. 요일은 기존 `repeat_weekday` 컬럼을 그대로 재사용해서 "매월 ○째 주 ○요일" 조합을 표현함(예: 마지막 주=-1 + 수요일=3 → "매월 마지막 주 수요일").
  - 넷째 주를 그냥 숫자 4로 고정하지 않고 "마지막 주"를 -1로 따로 표현한 이유: 어떤 달은 그 요일이 4번, 어떤 달은 5번 있을 수 있어서(예: 수요일이 있는 주가 4주인 달도, 5주인 달도 있음), 항상 "4번째"로 고정하면 5주 있는 달엔 진짜 마지막 주를 놓치게 됨. -1로 표현해서 매달 정확히 "그 달의 마지막 ○요일"을 가리키도록 함.
  - 마감일(다음 예정일) 계산도 새로 추가: 매월 옵션을 고르면 그 달의 "N째 주 ○요일" 날짜를 직접 계산해서 "매월 마지막 주 수요일 · 9월 30일 (수)"처럼 다음 예정일까지 같이 보여줌.
- **업무 추가/수정 화면**: 반복 선택에 "매월"을 추가하고, 매월을 고르면 "몇째 주"(첫째~넷째 주/마지막 주) + "요일" 두 드롭다운이 나란히 뜨도록 함(마감일 입력란은 반복 업무라서 그대로 숨김).
- **묶음 목록**: 지난번에 만든 일일업무/요일별 주간업무/개인업무 묶음 구조에 "월간 업무" 묶음을 하나 추가함(요일별로 또 쪼개지 않고 매월 반복 업무는 전부 한 묶음으로 모음 - 개수가 많지 않을 거라 예상돼서). 순서는 일일 업무 → 요일별 주간업무 → 월간 업무 → 개인 업무.
- **테스트 중 발견해서 같이 고친 부분**: 처음 구현했을 때 "월간 업무" 묶음이 페이지를 열면 기본적으로 접힌 채로 시작해서, 클릭해서 펼쳐야만 그 안의 "수정" 버튼 등을 쓸 수 있었음. 요일별 묶음은 7개나 되니 오늘 요일 것만 기본으로 펼쳐두는 게 맞지만, 월간 업무는 어차피 묶음이 하나뿐이라 접어둘 이유가 없어서 일일 업무·개인 업무처럼 기본으로 펼쳐진 상태로 시작하도록 고침.
- Playwright로 검증: (1) "매월" 선택 시 "몇째 주"+"요일" 필드가 같이 나타나고 마감일 필드는 숨겨지는지, (2) "매월 마지막 주 수요일"로 업무를 등록하면 실제 전송되는 값(`repeat_type: monthly, repeat_weekday: 3, repeat_week_ordinal: -1`)이 정확한지, (3) 등록 후 "월간 업무" 묶음으로 정상적으로 묶이고 "매월 마지막 주 수요일 · 9월 30일 (수)"처럼 다음 예정일이 맞게 표시되는지, (4) 수정 모달을 열었을 때 반복/요일/몇째주 값이 그대로 다시 채워지는지까지 4가지 모두 확인함.
- **이번엔 DB 스키마가 바뀌는 변경이라 `migration_35_tasks_monthly_repeat.sql`을 꼭 Supabase에서 먼저 실행해야 "매월" 옵션이 실제로 저장됨** (repeat_type 체크 제약 확장 + repeat_week_ordinal 컬럼 추가).

## 반복 업무에 "마지막 체크" 날짜 표시 (2026-09-02)

"선생님들이 언제 마지막으로 체크했는지도 뜨게끔 구현해줄 수 있어? 누락되고 있는지 파악하려고" 요청.

- 기존에는 반복 업무(매일/매주/매월)를 체크 해제하면 `last_completed_at`이 바로 `null`로 초기화됐음 — "이번 주기는 아직 안 했다"로 되돌리기 위한 로직이었는데, 그 부작용으로 "실제로 마지막에 언제 체크했었는지"에 대한 기록이 통째로 사라져 버렸음.
- 그래서 체크 해제해도 지워지지 않는 별도 컬럼 `last_checked_at`을 추가함. 체크할 때마다 지금 시각으로 갱신되고, 해제해도 그대로 남아있어서 "진짜 마지막으로 체크한 날짜"를 계속 추적할 수 있음(`last_completed_at`은 예전처럼 "이번 주기 완료 여부" 계산용으로만 계속 사용).
- 각 반복 업무 행에 "마지막 체크 9/2(수)"처럼 표시하고, 한 번도 체크한 적 없으면 "체크 기록 없음"을 빨간 글씨로 보여줌. 예를 들어 매주 반복인데 "마지막 체크 8/19(수)"처럼 2주 넘게 안 바뀌어 있으면 그 선생님이 최근 계속 누락하고 있다는 걸 한눈에 알아볼 수 있음. 반복 없는 개인 업무는 체크박스만으로 충분해서 표시하지 않음.
- 이 컬럼은 이번에 새로 생기는 거라, 지금까지의 체크 이력은 남아있지 않음(마이그레이션에서 현재 이번 주기에 체크되어 있는 것만 초기값으로 옮겨줌) — 오늘 이후로 체크하는 것부터 정확하게 기록이 쌓임.
- Playwright로 검증: (1) 오늘 체크된 매일 업무는 "마지막 체크 9/2(수)"로, 한 번도 체크 안 한 업무는 "체크 기록 없음"(빨간색)으로, 2주 전에 체크된 월간 업무는 "마지막 체크 8/19(수)"로 각각 올바르게 표시됨. (2) 체크를 해제해도 `last_checked_at`은 그대로 보존되고 `last_completed_at`만 초기화됨을 확인. (3) 다시 체크하면 `last_checked_at`이 지금 시각으로 갱신됨을 확인.
- **DB 스키마가 바뀌는 변경이라 `migration_36_tasks_last_checked_at.sql`을 Supabase에서 먼저 실행해야 함**(`last_checked_at` 컬럼 추가 + 기존 데이터 초기값 채우기).

## 업무 리포트 카카오톡 자동 발송 — 조사 결과 (구현 안 함, 2026-09-02)

"주간 업무리스트 설정을 걸어놓으면 카카오톡으로 보고를 줄 수 있어?"라는 질문에 대한 조사 결과. 아직 코드로 구현하지는 않았고, 가능 여부와 방법을 안내만 해드림.

- 처음엔 트레이너 선생님들도 같이 받는 걸 가정하고 알림톡/친구톡(사업자등록+템플릿심사 필요, 건당 비용)과 카카오워크 웹훅(무료, 별도 앱 설치 필요)을 조사해서 안내함.
- 이후 **호석님 본인만 받으면 된다는 걸 확인** — 그러면 훨씬 간단한 방법이 있음: **카카오 "나에게 보내기" API**(`/v2/api/talk/memo/default/send`). 카카오 디벨로퍼스에 무료로 앱을 등록하고 카카오 로그인으로 1회 동의만 받으면, 평소 쓰는 내 카카오톡 안의 "나와의 채팅"방으로 바로 메시지를 보낼 수 있음.
  - **사업자등록 불필요, 완전 무료**(발신자당 하루 100건 제한 — 개인 알림 용도로는 충분), 메시지 템플릿 사전 심사도 필요 없음(기본 템플릿만 사용, 텍스트 200자 제한 + 링크 버튼 1개).
  - 다만 access token이 6시간, refresh token이 2달마다 만료되기 때문에, 이 토큰들을 어딘가(Supabase 테이블 등)에 저장해두고 Vercel Cron이 주기적으로 자동 갱신해주는 로직이 필요함(안 하면 2달 뒤에 조용히 끊김) + 트레이너 그룹(카카오워크)과 달리 이건 개인용이라 정말로 호석님 계정으로만 1회 로그인 인증이 필요함.
  - 진행하려면: 호석님이 카카오 디벨로퍼스(developers.kakao.com)에 카카오계정으로 로그인 → 앱 하나 생성 → "카카오 로그인" 활성화 + "카카오톡 메시지 전송(talk_message)" 동의항목 설정, 이 과정만 호석님이 직접 해주셔야 하고(본인 계정 인증이라 대신할 수 없음) 나머지 자동 발송 로직(Vercel Cron + Supabase 토큰 저장 + 메시지 조립)은 구현해드릴 수 있음.
- 관련 목업 이미지 3종(카카오톡 알림톡/친구톡 스타일, 카카오워크 웹훅 스타일, 카카오 "나에게 보내기" 스타일)을 대화에서 전달함. 나중에 실제로 진행하기로 하면 이 README에도 구현 섹션으로 정리할 예정.

## 업무 리스트에 "시간" 지정 추가 (2026-09-02)

카카오톡 알림 관련 대화 중, 카카오톡 알림은 트레이너 선생님들이 아니라 **호석님 본인만** 받으실 거고, "10시 미팅 회의", "오후 3시 OO쌤 미팅"처럼 하루 중 정해진 시각이 있는 일정을 몇 분 전에 미리 알림 받고 싶다는 걸 확인함. 실제 카카오톡 자동 발송(이건 호석님이 카카오 디벨로퍼스에서 1회 인증해주셔야 진행 가능)에 앞서, 우선 업무 리스트 자체에 "몇 시"인지 등록할 수 있는 기반을 먼저 만듦 — 이것만으로도 회의/미팅 시각이 목록에서 바로 보이고 시간순으로 정렬돼서 그 자체로 유용함.

- `tasks` 테이블에 `due_time`(시:분) 컬럼을 추가함. 반복 없음/매일/매주/매월 어떤 설정과도 같이 쓸 수 있어서, "오늘 10시 회의"(1회성) 뿐 아니라 "매주 화요일 오후 3시 회의"(반복)처럼 반복 업무에도 시간을 붙일 수 있음.
- 업무 추가/수정 화면에 "시간 (선택)" 입력칸을 추가함. 시간을 넣으면 목록에 "매주 화요일 · 9월 8일 (화) · 오후 3:00"처럼 마감 라벨 맨 뒤에 시간이 붙어서 표시됨.
- 같은 묶음(개인 업무 등) 안에서 시간이 있는 업무들은 이른 시간순으로 먼저 보이고, 시간이 없는 업무는 뒤로 가도록 정렬을 바꿈 — "10시 회의"가 "오후 3시 미팅"보다 항상 위에 오는 식.
- Playwright로 검증: (1) 시간이 뒤섞여 등록된 업무들이 개인 업무 묶음 안에서 10시→오후 3시→시간 없음 순서로 정렬되는지, (2) 새 업무 등록 시 입력한 시간이 그대로 저장되는지, (3) 수정 모달을 열었을 때 저장된 시간이 다시 채워지는지 모두 확인함.
- **다음 단계(아직 미착수)**: 이 `due_time`을 기준으로 "몇 분 전에" 카카오톡 알림을 보내주는 기능은, 호석님이 카카오 디벨로퍼스에서 앱 등록 + 카카오 로그인 동의(talk_message)를 1회 완료해주셔야 실제 발송 로직(토큰 저장/자동 갱신 + 주기적으로 다가오는 일정 확인해서 발송)을 구현할 수 있음. 자세한 절차는 이전 대화 내용 참고.
- **DB 스키마가 바뀌는 변경이라 `migration_37_tasks_due_time.sql`을 Supabase에서 먼저 실행해야 함**(`due_time` 컬럼 추가).

## OT 연락 미응답 → OT1 날짜 확정 시 확인 팝업이 계속 뜨는 문제 수정 (2026-09-02)

"OT 미응답 회원님들 추가해뒀다가 답장 와서 스케줄 옮기려고 날짜만 클릭하면 자꾸 확인창이 떠서 날짜 입력을 못하겠다"는 문의(아이폰 화면 스크린샷 2장 첨부).

- 원인: "OT1 날짜 확정" 칸이 날짜를 입력하는 즉시(`onchange`) "OT1로 옮길까요?" 확인 팝업을 띄우도록 되어 있었는데, **아이폰(iOS Safari)에서는 날짜 입력칸의 달력(휠 피커)을 스크롤하는 도중에도 change 이벤트가 계속 발생함** — 최종적으로 날짜를 다 고르기도 전에, 휠이 한 칸씩 움직일 때마다 change가 발생해서 그때마다 확인 팝업이 떠버렸던 것. 그래서 사용자 입장에서는 날짜를 고르려고 스크롤만 했는데 팝업이 계속 튀어나오는 것처럼 느껴졌음.
- `onchange` 대신 `onblur`(입력칸에서 포커스가 벗어났을 때)로 연결을 바꿔서, 날짜를 다 고르고 다른 곳을 탭했을 때 딱 한 번만 확인 팝업이 뜨도록 고침. 날짜 고르는 도중에는 아무 반응이 없다가, 다 고르고 나면 그제서야 "OO님을 OO일 OT1로 옮길까요?"가 한 번 뜨는 방식.
- 코드 배포만으로 해결되는 수정이라 **별도 SQL 실행은 필요 없음**.
- Playwright로 검증: (1) 날짜를 고르는 중간에 change 이벤트가 여러 번 발생해도(아이폰 휠 스크롤 상황 재현) 확인 팝업이 뜨지 않는지, (2) 입력칸에서 포커스가 벗어나면(blur) 그제서야 팝업이 정확히 한 번만 뜨는지, (3) 확인을 누르면 실제로 OT1 표로 정상 이동(리드 등록 + 미응답 목록에서 삭제)되는지까지 확인함.

## 바디코디 전체 회원 데이터 이전 준비 (2026-09-02)

"바디코디를 gym-ops로 완전히 대체하고 싶다"는 목표로, 실제 바디코디에서 내보낸 "평산점 총 회원관리 시트.xlsx"(1,734명, 29개 컬럼)를 직접 받아서 검증함. 아직 실제 등록은 안 했고(사용자가 직접 회원 관리 화면에서 업로드해야 함), 그 전에 기존 "엑셀 일괄 업로드" 기능이 이 실제 파일을 얼마나 정확히 처리하는지 미리 전부 시뮬레이션해서 문제를 찾아 먼저 고쳐둠.

- 형식은 기존에 이미 지원하던 "① 기존 프로그램 내보내기" 형식(이름+이용권정보 컬럼)으로 자동 인식됨 — 새 코드를 만들 필요 없이 기존 업로드 기능을 그대로 씀.
- 실제 1,734명 데이터를 놓고 파싱 로직을 검증하다가 실제 버그 하나를 찾아서 고침: **"1:1 PT" 상품인데 앞에 "(PT)" 태그가 안 붙은 줄(유료 PT 일부)이 전부 "이용권(멤버십)"으로 잘못 분류되고 있었음** — PT 잔여횟수가 아예 안 들어갈 뻔한 문제. `(PT)` 태그 유무와 상관없이 "1:1 PT"/"1:1PT" 텍스트가 있으면 PT로 인식하도록 `parseMembershipInfo()`를 고침 (`members.html`).
- **무료 1:1 PT 체험(예: "무료 1:1 PT 30분")은 실제 PT 등록이 아니므로 아예 제외하도록 수정함** — 처음엔 위 수정으로 무료 체험도 PT 잔여횟수로 잡히고 있었는데, "무료 1:1PT는 빼야지"라는 지적을 받고 바로잡음. "체험"이 들어간 줄과 마찬가지로, "무료"와 "1:1 PT"/"1:1PT"/"(PT)"가 같이 들어간 줄은 어떤 카테고리에도 안 넣고 건너뜀(실제 파일 기준 60줄, 58명 해당). 반대로 "무료"라는 글자가 없는 진짜 유료 PT는 그대로 정상적으로 PT 잔여횟수에 반영됨.
- 데이터 품질 이슈도 하나 발견해서 같이 고침: 바디코디에서 생년월일을 입력 안 한 회원은 등록일을 그대로 생년월일 칸에 채워넣는 경우가 있었음(1,685명 중 598명이 생년월일=등록일과 완전히 동일) — 그대로 가져오면 가짜 생년월일이 들어가므로, 생년월일이 등록일과 똑같으면 미입력으로 보고 비워서 가져오도록 함(`buildPayloadFromExportRow()`).
- 사용자에게 확인한 것: 이용권 이력이 아예 없는 회원(993명, 약 57%)도 전부 등록하기로 함(향후 재등록 대상으로 관리하고 싶다는 이유).
- 검증 방법: 실제 파일을 Python으로 직접 파싱해서(수정된 로직을 그대로 이식) 1,733명(이름 없는 1행 제외) 전원의 등록 예정 결과를 미리 계산 — 개인PT 정보 85명·그룹PT 71명·이용권(멤버십) 657명·락커 359명·운동복 340명·아무 이용권 정보 없이 인적사항만 있는 회원 975명, 전화번호 없는 행 0건, 오류로 처리 실패하는 행 0건까지 확인함. 실제 등록 시에도 한 행 처리가 실패해도 나머지는 계속 진행되도록 이미 되어 있음(행별 try/catch).
- **다음 단계**: 사용자가 이 zip을 재배포한 뒤, 회원 관리 화면의 "엑셀 일괄 업로드"에 원본 파일을 그대로 올리면 됨(파일을 따로 가공할 필요 없음). SQL 실행은 필요 없음(코드 수정만으로 해결되는 변경).

### 주기적으로 이 파일을 다시 올리는 경우 (2026-09-02)

바디코디에서 최신 파일을 받아서 gym-ops에 주기적으로 재업로드("최신화")하는 것에 대한 안전성 검토:

- **속도 저하 걱정은 안 해도 됨**: 이 업로드는 그 순간에만 실행되는 일회성 배치 작업임(회원 1명당 조회 1번 + 등록/수정 1번씩, 순차 처리라 1,700명 기준으로 몇 분 정도 걸림 — 업로드 화면에도 이미 "몇 분 걸릴 수 있어요" 안내가 있음). 앱을 평소에 쓸 때 느려지는 것과는 무관하고, 업로드가 끝나면 그걸로 끝임.
- **회원이 삭제될 위험은 없음**: 이 기능은 파일에 있는 회원을 전화번호 기준으로 새로 만들거나(신규) 기존 정보를 덮어쓰는(업데이트) 방식이라서, 파일에 없는 기존 gym-ops 회원이 지워지는 일은 없음.
- **다만 진짜 위험은 "덮어쓰기"임**: 업로드는 전화번호가 같으면 무조건 바디코디 쪽 값으로 덮어씀. 그래서 gym-ops에서 직접 손으로 고친 값(예: PT 잔여횟수를 수기로 보정했거나, 만료일을 따로 수정한 경우)이 있다면, 그 이후에 바디코디 파일을 다시 올리는 순간 그 수정 내용이 바디코디 쪽 값으로 되돌아가 버림. 반대로 gym-ops에서만 입력하고 바디코디에는 없는 정보(있다면)도 마찬가지로 덮어써질 수 있음.
- 이 위험은 "바디코디와 gym-ops를 당분간 같이 쓰다가 나중에 gym-ops로 완전히 넘어가는 과도기적 상황"인지, 아니면 "앞으로도 계속 바디코디에서 내보내서 정기적으로 동기화하는 방식"인지에 따라 대응이 달라짐 — 후자라면 수기로 고친 값은 덮어쓰지 않도록 보호하는 로직을 추가로 만드는 게 좋음.
- **확인 결과(사용자 답변)**: PT 잔여횟수는 관리자(호석님)가 바디코디 스케줄표를 보고 gym-ops PT 스케줄러에 직접 그대로 입력하는 구조라서, 두 시스템의 잔여횟수가 항상 같은 근거로 맞춰짐 → 재업로드로 인한 잔여횟수 덮어쓰기 위험은 실질적으로 없음. 별도 보호 로직은 만들지 않기로 함. (다만 나중에 선생님들에게 gym-ops 출석 처리 권한을 직접 주게 되면 이 얘기를 다시 짚어봐야 함 — 그때는 gym-ops에서 잔여횟수가 독자적으로 바뀌게 됨.)

### 이름 칸에 섞여 들어온 상품 분류 태그 제거 (2026-09-02)

실제 등록 후 "PT그룹PT 최지인 회원이 등록 안 된 것 같다"는 문의가 있어서 재확인함 — 결론적으로 등록은 됐지만, 바디코디 원본 파일의 "이름" 칸 자체에 상품 분류 태그가 그대로 붙어서 들어오는 경우가 있었음(예: 실제 이름은 "최지인"인데 파일에는 "PT그룹PT 최지인"으로 들어있음). 이런 이름 앞에 "PT", "그룹PT", "체험단", "PT환불" 같은 태그가 붙은 행이 실제 파일에 **299건(전체의 약 17%)** 있었음 — 검색(회원 관리의 검색창)으로는 부분 일치라 그래도 찾을 수 있지만, 이름이 이상하게 보이고 가나다순으로 봤을 때도 엉뚱한 위치("ㅊ" 최지인이 아니라 "P"/"PT..." 쪽)로 밀려서 찾기 어려웠던 것으로 보임.

- `members.html`에 `cleanMemberName()` 함수를 추가해서, 이름 맨 앞에 붙은 "PT환불"/"PT"/"그룹"/"환불"/"체험단"/"체험" 태그를(여러 개 겹쳐 있어도 반복해서) 다 떼어내고 실제 이름만 남기도록 함(`buildPayloadFromExportRow()`에 적용). 실제 파일 기준 308건이 이 대상이었고, 태그를 떼고 나서 이름이 아예 없어지는 경우는 0건이었음(전부 진짜 이름이 남음).
- 업로드는 전화번호 기준 upsert라서, **이 zip으로 같은 원본 파일을 다시 한번 업로드하면 이미 등록된 회원들의 이름도 자동으로 깨끗하게 정리됨**(새로 등록하는 게 아니라 기존 회원 정보가 업데이트되는 것 — 회원이 중복 생성되지는 않음). 별도로 회원을 하나씩 수정할 필요 없음.
- 코드 수정만으로 해결되는 변경이라 별도 SQL 실행은 필요 없음.

### 회원이 1,000명을 넘으면서 회원 목록/검색에서 일부가 통째로 안 보이던 문제 (2026-09-02)

이름 태그 정리 후에도 "최지인/고수아 회원이 이름으로도, 전화번호로도 검색이 안 된다"는 문의가 계속돼서 더 깊게 파봄 — 실제 원인은 이름 문제가 아니라 훨씬 근본적인 문제였음.

**원인**: Supabase(내부적으로 PostgREST라는 걸 씀)는 한 번의 조회 요청에 `limit`(몇 개까지 가져올지)을 따로 안 주면, 서버 쪽 기본 설정값(보통 1,000행)에서 **에러 없이 조용히 잘라서** 응답을 돌려줌. gym-ops 코드는 회원 목록을 불러올 때(`fetchMembers()`, 회원 관리 화면·PT 스케줄·업무 리스트·매출 입력 등 회원 검색이 들어가는 모든 화면이 이 함수 하나를 같이 씀) 이 제한을 감안하지 않고 그냥 한 번에 다 가져오려고 했었음. 회원이 1,000명 미만일 때는 문제가 전혀 없다가, 이번에 바디코디 회원 1,734명을 한 번에 등록하면서 전체 회원 수가 1,000명을 넘어가자, 뒤쪽에 있는 회원들이 화면(검색 포함)에 아예 안 뜨게 된 것. 최지인/고수아님은 실제로는 데이터베이스에 정상적으로 등록·업데이트돼 있었지만, 앱이 애초에 그 회원들을 서버에서 불러오지도 못했던 것이라 검색을 해도 나올 수가 없었음(전화번호로 검색해도 못 찾은 것도 같은 이유).

- `fetchMembers()`가 결과가 빈 배열로 끝날 때까지 `limit`/`offset`을 바꿔가며 반복 조회해서, 회원이 몇 명이든 전체를 다 가져오도록 고침(`data.js`에 공용 함수 `fetchAllRows()` 추가).
- 홈 화면의 "데이터 백업"(엑셀로 전체 데이터 내려받기) 기능도 같은 문제가 있어서(회원 수가 1,000명을 넘으면 백업 파일에도 일부가 빠짐) 같이 고침.
- 이 문제는 회원 목록에 국한된 게 아니라, 앞으로 매출/TM기록/업무 등 다른 데이터도 누적돼서 1,000건을 넘기면 같은 방식으로 재발할 수 있는 구조적인 문제였음. 우선 가장 빨리 1,000건을 넘길 가능성이 큰 회원 목록/백업부터 고쳤고, 필요하면 다른 목록에도 같은 패턴을 적용할 수 있음.
- 코드 수정만으로 해결되는 변경이라 별도 SQL 실행은 필요 없음. **이 zip을 배포한 뒤에는 파일을 다시 업로드할 필요 없이(이미 다 정상적으로 등록되어 있었으므로) 그냥 회원 관리 화면에서 최지인/고수아로 다시 검색해보면 바로 나올 것으로 예상됨.**

## "방문 빈도 저조 회원" 관리 기능 — 목업만 먼저 제공 (2026-09-03)

"만료회원이 아니어도, 최근 방문이 뜸해진 회원을 한 달 전부터 쭉 나열해서 TM 돌리고 싶다"는 요청이 있었음(바디코디에도 "최근방문일"이 있다고 함). 사용자가 "바로 만들진 말고 어떻게 구현할지 이미지로 먼저 보여달라"고 해서, 아직 실제 코드는 안 만들고 `expiry.html`(만료회원·TM) 페이지에 "🚶 방문 빈도 저조" 탭을 추가하는 방식의 정적 목업 이미지(스타일은 실제 style.css 그대로 사용)만 만들어서 보여줌. 기존 TM 상태 기록(연락함/재등록예정 등) 인프라를 그대로 재사용하는 설계로 제안함.

- 계획: `members`에 `last_visit_date` 컬럼 추가 → 바디코디 재업로드 시 "최근방문일" 컬럼도 같이 가져오도록 확장(gym-ops 자체엔 출입 체크인 기능이 없어서 이 값의 원본은 계속 바디코디임) → 미방문일수(오늘 - last_visit_date) 기준 15/30/60/90일 필터 + 정렬로 목록 표시.
- **아직 사용자 확인 대기 중** (다음 대화에서 답변 받으면 진행): ① 이용권 살아있는 회원만 보여줄지 만료된 회원도 섞을지, ② 방문기록 자체가 없는 회원을 어떻게 다룰지. 실제 구현(마이그레이션 + expiry.html 코드)은 아직 안 함.

## 주차별 매출 기록에서 "등록" 처리 시 PT 회원 관리에 자동 추가 (2026-09-03)

`pt.html`의 "주차별 매출 기록"(상담/OT 리드 시트, `pt_leads` 테이블)에서 확률 칸을 "등록"으로 바꾸면, 그 회원이 "PT 회원 관리"(`pt_care_logs`, 재등록 케어용 월별 시트)에 자동으로 추가되도록 구현함. 원래 "이월" 처리 시 다음 달로 자동 이관되는 기존 로직(`carryOverLeadToNextMonth`, `carryOverCareLogToNextMonth`)과 같은 패턴을 그대로 재사용함.

- `pt.html`에 `addLeadToCareManagement(lead)` 함수를 추가하고, `handleProbChange()`에서 확률 값이 `'registered'`(등록)가 될 때 호출하도록 연결함.

## 배포 후 옛날 자바스크립트가 캐싱되는 문제 수정 (2026-09-03)

배포 후 "upsertMarketingInquiry is not defined"라는 오류가 발생한다는 리포트를 받음. 코드 자체는 문제없었음(로컬 테스트로 재확인) — 원인은 **브라우저(또는 Vercel CDN)가 `data.js`를 옛날 버전으로 캐싱**해서 새로 배포해도 일부 사용자 화면에서는 계속 예전 파일이 쓰이는 문제였음. 이 프로젝트는 파일명이 매번 그대로(`data.js`, `config.js`, `auth.js`, `style.css`)라서 브라우저가 "저번에 받은 파일이랑 이름이 같으니 새로 안 받아도 되겠지"라고 판단하고 캐시에 있는 옛날 파일을 계속 쓸 수 있음.

- 모든 HTML 파일(15개)에서 `<script src="data.js">` 같은 태그를 `<script src="data.js?v=(숫자)">` 형태로 바꿈 — 뒤에 붙는 `?v=...` 덕분에 브라우저가 "파일명은 같아도 주소가 다르니 새로 받아야 하는 파일"로 인식해서 캐시를 안 쓰고 새로 받아옴. `config.js`/`auth.js`/`data.js`/`style.css` 4개 파일 전부에 적용.
- **앞으로 배포할 때마다** 이 `?v=` 뒤의 숫자를 새로 바꿔야 이 문제가 재발하지 않음 — 이후 세션(저)이 zip을 새로 만들 때마다 이 숫자를 자동으로 새로 바꿔서 포함하기로 함. 혹시 배포했는데도 화면이 안 바뀌면 이 숫자가 바뀌었는지 확인하면 됨(안 바뀌었으면 캐싱 문제가 다시 생긴 것).
- 사용자 쪽에서도 화면이 이상하면 강력 새로고침(Ctrl+Shift+R 또는 Cmd+Shift+R)을 먼저 시도해보시면 됨 — 이번 조치 이후로는 그럴 일이 크게 줄어들 것으로 예상됨.

## "오늘" 문의 경로 칸이 자정 넘어도 안 바뀌는 문제 수정 (2026-09-03)

브라우저 탭을 안 끄고 밤새 그대로 켜놓으면(사무실 컴퓨터에서 흔함) 자정이 지나도 "오늘" 문의 경로 칸이 새로고침 없이는 다시 그려질 계기가 없어서 어제 날짜 기준 숫자가 그대로 남아있는 문제였음(어제 데이터 자체는 DB에 정상 저장돼 있었지만, 화면이 "오늘 것"이라고 보여주는 칸이 갱신이 안 됨).

- `dashboard.html`에 1분마다(그리고 탭을 다시 볼 때마다 - `visibilitychange` 이벤트) 날짜가 바뀌었는지 확인하는 타이머를 추가함(`refreshInquiryIfDateChanged()`). 날짜가 바뀐 걸 감지하면 그 달 문의 경로 데이터를 서버에서 다시 불러와서 "오늘" 칸과 "지난 기록" 표를 둘 다 새로 그림 — 그러면 어제 칸은 지난 기록 표에 그대로 남고, 오늘 칸은 자동으로 빈 채로 새로 나타남.
- Playwright로 검증: 브라우저의 `Date`를 어제 날짜로 고정해서 페이지를 열고(어제 데이터가 "오늘" 칸에 뜸을 확인) → `Date`를 실제 오늘로 바꾸고 날짜 감지 함수를 호출 → "오늘" 칸이 새 날짜 기준으로 다시 그려지면서 빈 칸으로 바뀌고, 서버에 다시 요청이 나가는지 확인함.

## 매출 보고 "이미지 복사" 버튼 추가 (2026-09-03)

공유 링크 기능을 만든 뒤 "저 페이지를 열어보는 링크 말고, 예전에 캡쳐해서 보내던 것처럼 이미지 파일 자체를 바로 보내고 싶다"는 피드백을 받아서 처음엔 "이미지로 저장"(PNG 파일 다운로드) 버튼으로 추가함(사용자가 실제 캡쳐 화면 예시를 보내줌 - 일간 매출 보고 + 이번 달 매출 + 상품별 재등록 현황 + 최근 매출 내역 + 문의 경로 + 워크인이 위아래로 쭉 이어진 화면 전체). 그런데 "저장하면 컴퓨터에 파일이 쌓이고, 저장한 걸 다시 열어서 복사하는 게 번거롭다 — 그냥 눌렀을 때 바로 복사돼서 단톡방에 Ctrl+V로 붙여넣을 수 있으면 좋겠다"는 피드백을 받아서, 파일로 저장하는 대신 클립보드로 바로 복사하도록 다시 고침.

- "매출 보고" 제목 옆의 버튼 이름을 "🖼️ 이미지 복사"로 바꿈(기존 "🔗 공유 링크 만들기" 버튼 옆). 누르면 지금 화면에 보이는 대시보드 내용(매출 보고 ~ 워크인/미스까지, 사용자가 보내준 캡쳐 화면과 동일한 범위)을 그대로 이미지로 만든 뒤 **파일로 저장하지 않고 클립보드에 바로 복사**함 — 카카오톡 단톡방 등 채팅창에서 Ctrl+V(붙여넣기)만 하면 바로 전송됨. 공유 링크 관련 버튼·패널은 이미지에는 안 나오도록 뺐음(리포트 내용만 깔끔하게 담기게).
- **클립보드 복사가 안 되는 상황 대비**: 구형 브라우저이거나 클립보드 쓰기 권한이 거부된 경우엔 자동으로 예전 방식(파일 다운로드, `매출보고_YYYYMMDD.png`)으로 대체되고 그 사실을 토스트 알림으로 알려줌 — 어떤 경우든 이미지 자체는 항상 받을 수 있음.
- 공유 링크 기능은 그대로 남겨둠 — 채팅에 바로 붙여넣을 이미지가 필요하면 "🖼️ 이미지 복사", 클릭 한 번으로 볼 수 있는 링크가 필요하면 "🔗 공유 링크 만들기"를 상황에 맞게 골라 쓰면 됨.
- **구현 방식**: 이 프로젝트는 원래 "외부 CDN 없이 순수 CSS/JS만 사용"이 원칙이었는데(`style.css` 맨 위 주석 참고), 화면에 보이는 걸 그대로 이미지로 캡쳐하는 기능은 브라우저 자체 기능만으로 만들 방법이 없어서 `html2canvas`라는 외부 자바스크립트 라이브러리를 예외적으로 CDN(cdnjs)에서 불러와 씀. 클립보드 복사는 브라우저의 Clipboard API(`navigator.clipboard.write` + `ClipboardItem`)를 사용하며, HTTPS 환경(Vercel 배포본)에서 정상 동작함. 이 버튼을 쓸 때만 인터넷에서 라이브러리를 받아오고, 못 받아오면(오프라인 등) 버튼을 눌렀을 때 안내 메시지만 뜨고 나머지 화면은 평소처럼 정상 동작함 — 다른 기능에는 영향 없음.
- Playwright로 검증(실제 cdnjs는 이 개발 환경 네트워크에서 막혀 있어서 `html2canvas` 스크립트를 가짜로 흉내 낸 스텁으로 대체해서 테스트함): 클립보드 쓰기 권한이 있을 때 정상적으로 복사되고 파일 다운로드는 발생하지 않는지, 클립보드 쓰기가 거부(reject)됐을 때 자동으로 파일 다운로드(`매출보고_YYYYMMDD.png`)로 대체되고 그에 맞는 안내 토스트가 뜨는지, "공유 링크 만들기"/공유 관련 패널처럼 `no-capture` 클래스가 붙은 요소는 캡쳐 대상에서 걸러지는지 확인함. 실제 배포 환경(Vercel, 사용자 인터넷 연결·브라우저)에서 클립보드 복사가 실제로 되는지는 사용자가 직접 눌러보며 최종 확인 필요.

## "이미지 복사"했을 때 문의 경로/워크인 칸 숫자가 잘려 보이는 문제 수정 (2026-09-03)

"복사해서 붙여넣기하면 이미지 자세히 보면 숫자가 살짝 안 보이거든? 칸에 딱 맞게 안 나오고 반만 숫자가 잘려서 나와"라는 피드백으로 수정.

- **원인 1(진짜 원인)**: `html2canvas`는 `<input>` 안의 글자를 직접 캔버스에 다시 그리는 방식으로 동작하는데, 이 계산이 부정확해서 문의 경로/워크인 표의 숫자 입력칸 글자가 위아래로 살짝 잘려 보이는 걸로 확인됨(브라우저 화면 자체에서는 정상으로 보임 - 캡쳐/복사할 때만 나타나는 `html2canvas`의 알려진 한계). 이걸 고치려고, 이미지를 만들 때만(`onclone` 콜백 - 화면에 실제로 보이는 것과는 별개인, 캡쳐 전용으로 복제된 문서) 입력칸을 그 값이 그대로 보이는 일반 텍스트 칸으로 순간적으로 바꿔치기하도록 함. 실제 화면의 입력칸(타이핑 가능한 상태)은 전혀 안 건드리고 그대로 살아있음 - 이미지에만 반영됨.
- **원인 2(같이 발견한 부수적인 문제)**: 대시보드의 문의 경로/워크인 입력칸이 `sheet-input`이라는 클래스를 쓰고 있는데, 정작 이 클래스의 스타일 정의 자체가 대시보드 페이지에는 없어서(PT 관리 페이지에는 있었는데 대시보드에는 빠져 있었음) 브라우저 기본 숫자칸 모양(굵은 회색 테두리)으로 보이고 있었음. 다른 페이지(PT 관리)와 똑같은 깔끔한 스타일(테두리 없음, 호버 시에만 살짝 테두리)로 맞춰서 이미지 캡쳐뿐 아니라 화면에서 보는 모습도 더 일관되게 고침.
- Playwright로 검증(실제 html2canvas는 개발 환경 네트워크에서 막혀 있어서, `onclone` 콜백을 실제로 실행해보는 스텁으로 대체해서 테스트함): 캡쳐용으로 복제된 문서에는 `<input>` 요소가 하나도 안 남고 값이 그대로 텍스트로 바뀌는지, 캡쳐 이후에도 실제 화면의 입력칸은 여전히 정상 작동(타이핑 가능하고 값 유지)하는지 확인함. 실제 배포 환경에서 카톡 등에 붙여넣었을 때 숫자가 온전히 다 보이는지는 사용자가 직접 확인 필요.

## "상담 워크인/미스 표가 9월에 고정된 것 같다"는 문의 확인 (2026-09-04)

"이거 왜 9월달꺼로 고정을 해놨어 ㅋㅋ 10월 페이지로 넘어가면 9월달 데이터는 그대로 두고 10월달 페이지는 초기화가 되어야지"라는 피드백(9월 표에서 1주차 월요일 칸, 5주차 목/금 칸이 회색으로 비활성 처리된 스크린샷과 함께)을 받고 코드/동작을 직접 검증함.

- **결론: 원래부터 버그가 아니었음.** `renderWorkinTable()`은 항상 `new Date()`(실제 오늘 날짜)를 기준으로 그 달의 주차를 다시 계산하고(`weekBucketsForMonth`), 표에 채워지는 데이터도 `fetchWorkinResults(currentMonthStr())`로 **딱 그 달 범위(`result_date >= 이번달 1일 AND < 다음달 1일`)만** DB에서 불러옴 — 즉 9월에 다 입력해두고 10월로 날짜가 넘어가면(=달력상 실제 오늘 날짜가 10월이 되면) 10월 페이지는 자동으로 빈 칸(초기화된 화면)에서 새로 입력하게 되고, 9월에 입력했던 기록은 DB에 그대로 남아있음(안 지워짐 - 나중에 필요하면 복구/조회 가능한 상태로 보존됨). 코드를 고칠 필요가 없어서 기능 자체는 바꾸지 않았음.
- **다만 화면 UI 자체가 "이번 달"이라고만 써 있고 몇 년 몇 월인지 숫자가 안 보여서**, 실제로 달이 넘어가도 눈으로 봤을 때 "진짜 갱신된 게 맞나?"를 확인할 방법이 없었음 — 이게 "9월로 고정된 것 같다"는 오해의 실제 원인으로 보임. 그래서 표 제목을 "상담 워크인 / 미스 (이번 달, 주차별)"에서 **"상담 워크인 / 미스 (2026년 10월, 주차별)"처럼 연/월 숫자가 실제 오늘 날짜 기준으로 항상 같이 보이도록** 고침(`workinMonthLabel`).
- **검증 방법**: Playwright에서 브라우저의 `Date`를 2026년 10월 15일로 가짜로 바꿔치기한 뒤(실제 시스템 날짜는 그대로 9월), 9월 기록과 10월 기록을 각각 섞어서 응답하는 가짜 서버로 대시보드를 열어서 확인함 — (1) 표 제목이 "2026년 10월"로 정상적으로 바뀌는지, (2) 총 성공/실패 건수가 10월 데이터만 반영하고(9월 기록 99건은 안 섞임) 10월 기록만 정확히 합산되는지(성공 12건, 실패 1건), (3) 주차별 칸 활성/비활성 상태가 실제 10월 달력과 맞는지 스크린샷으로 확인함.
- **중요 — 10월 달력은 사용자가 예상한 것과 반대 패턴임**: "다음달에는 월요일, 마지막주 목/금 칸을 쓸 텐데"라고 예상하셨지만, 실제 2026년 10월은 1일이 목요일(10/1=목, 10/2=금)이라서 **10월 1주차는 오히려 월/화/수가 비활성(9월 날짜라서)이고 목/금만 활성**됨. 반대로 **10월 마지막 주(5주차, 10/26~10/30)는 월~금이 전부 10월 안에 들어와서 5칸 다 활성**됨 — 9월과는 정반대 모양임. 이건 매달 1일이 무슨 요일인지에 따라 매번 달라지는 정상적인 달력 계산 결과라서 손댈 부분이 아님.

- 공유 링크/이미지 복사 기능(`buildReportSnapshot()`)도 같이 맞춤 — 화면에 지금 7월이 떠 있는 상태에서 공유하면, 공유되는 스냅샷의 "이번 달 매출"·"상품별 재등록 현황"·"워크인/미스"도 7월 기준으로 찍힘(화면에 보이는 그대로 공유된다는 이 기능의 기존 원칙 그대로 유지). 단, "문의 경로"는 여전히 실제 오늘 기준으로 찍힘(위와 같은 이유).
- 자정이 지나 실제 날짜가 바뀌는 경우를 감지하는 기존 워처(`refreshInquiryIfDateChanged`, 1분마다 체크)도 손봄 — 사용자가 화살표로 다른 달을 보고 있는 도중에 자정이 지나도 화면이 강제로 오늘로 안 바뀌게 하고(보고 있던 과거 데이터가 갑자기 사라지는 걸 방지), 반대로 "오늘"을 보고 있던 상태에서 자정이 지나면 자동으로 새 오늘 날짜를 따라가도록 함.
- Playwright로 검증: 월간 탭에서 화살표로 9월→8월→7월로 이동 시 세 섹션 제목/숫자가 전부 7월 기준으로 바뀌는지(월간 총매출 500,000원, 상품별 재등록 50%, 워크인 성공 5건), "오늘" 버튼을 누르면 다시 9월(실제 오늘) 숫자로 정확히 복귀하는지, 일간 탭에서 화살표를 5번 눌러 9/4→8/30으로 달을 건너뛰었을 때도 이 세 섹션이 자동으로 8월로 바뀌는지, 7월을 보고 있는 상태에서 공유 링크를 만들면 스냅샷에도 7월 데이터가 찍히는지 확인함.

## 화살표로 8월을 봤을 때 "1주차가 통째로 씹혀 보이는" 버그 수정 + 문의 경로도 지난 달까지 같이 보기 (2026-09-04)

위 기능을 실제 배포 사이트에서 써보신 사용자가 스크린샷과 함께 두 가지를 지적함: (1) 매출 보고 화살표로 8월을 봤을 때 워크인/미스 표가 "1주차" 없이 "2주차"부터 시작하는 것처럼 보임, (2) 문의 경로 "지난 기록 보기" 표는 여전히 실제 오늘(9월) 데이터만 보여줘서 8월을 보는 중에도 안 바뀜 — "이런 정보도 나중에 데이터 추적·분석용 다른 프로그램을 만들 거라 중요하다"며 이것도 같이 움직이게 해달라고 요청함.

- **1번은 실제 버그였음.** `weekBucketsForMonth()`가 "그 달 1일부터 무조건 새 주차를 시작"하는 방식이었는데, 2026년 8월처럼 1일이 토요일인 달에서는 1일(토)·2일(일) 이틀만 있는 주차가 "1주차"로 먼저 만들어지고, 이 표는 월~금만 쓰기 때문에 그 "1주차"는 화면에 아무 날짜도 안 뜨는 완전히 빈 줄이 됨 — 그리고 진짜 그 달의 첫 평일 주(8/3~8/7)는 "2주차"로 밀려서 표시됨. 사용자가 본 "1주차가 씹힌 것 같다"는 게 정확한 관찰이었음. **토/일요일은 이 표에 애초에 안 쓰이므로 주차를 셀 때부터 건너뛰도록 고쳐서**, 이제 8월은 1주차가 8/3~8/7부터 정상적으로 시작함(9월처럼 원래 1일이 평일인 달에는 영향 없음 - 화면 그대로 동일).
- **2번은 새 요청으로 반영함.** 문의 경로의 "지난 기록 보기" 표(날짜별로 다 펼쳐서 보는 표)도 매출 보고 화살표로 지금 보고 있는 기준월을 그대로 따라가도록 바꿈 — 8월로 이동하면 이 표도 8/1~8/31 전체가 뜨고, 그 안의 숫자 칸을 클릭해서 예전 날짜 기록을 바로 고칠 수도 있음(워크인 표와 똑같은 방식). 다만 표 맨 위의 "오늘 칸"(카운터)은 그 성격상 실제 오늘 날짜에만 입력하는 게 맞아서(달을 이동했다고 "오늘"이 바뀔 수는 없으므로) 계속 실제 오늘 기준으로 남겨둠 — 즉 "오늘 칸"은 화살표와 무관하게 항상 실제 오늘, 그 아래 "지난 기록 보기" 표만 화살표를 따라감.
- Playwright로 검증: 8월(1일=토요일)로 이동했을 때 워크인 표 1주차가 "8/3~8/7"로 정상 표시되고 총 5주차(10개 행)가 나오는지, 문의 경로 지난 기록 표가 8/1부터 8/31까지 31행 다 뜨고 미리 넣어둔 가짜 8월 기록(8/5=4건, 8/20=9건)이 정확한 위치에 보이는지, 그 와중에도 "오늘 칸"은 여전히 실제 오늘(9/4) 기록만 보여주고 8월 데이터에 영향받지 않는지 확인함.

## 매출 보고 표를 날짜별 페이지로 나눔 (2026-09-04)

월간 매출 보고를 보고 있을 때 "이미지 복사" 버튼으로 캡쳐하면 그 아래 매출 내역 표가 한 달치 매출을 전부 한 표에 쭉 이어서 보여주는 방식이라 표가 너무 길어져서, 이미지로 만들면 스크롤을 한참 내려야 할 정도로 세로로 길어지는 문제가 있었음("9/1꺼만, 9/2꺼만 이렇게 뜨게끔... 10명 넘어가는 페이지 형식으로 만들어줘"). 어떤 방식을 원하시는지 확인해서(날짜별 페이지 vs 10건씩 고정 페이지 중 **날짜별 페이지**를 선택하심) 반영함.

- "매출 보고"의 매출 내역 표(위쪽 총매출/FC/PT 카드 아래, 회원명·항목·담당·결제수단·금액이 나오는 표)를 **1페이지 = 매출이 있던 날짜 하나**로 나눔 — 예를 들어 9월 전체를 보고 있으면 1페이지엔 9/3 매출만(그날 몇 건이든 상관없이 전부), 다음 화살표를 누르면 2페이지엔 9/2 매출만, 이런 식으로 최신 날짜부터 하나씩 넘겨봄. 표 아래 "◀ 2026-09-03 (1/2, 14건) ▶"처럼 지금 몇 번째 페이지인지, 그 날짜에 몇 건이 있는지 같이 보여줌.
- 위쪽 총매출/FC/PT 카드는 페이지 이동과 무관하게 **항상 선택한 기간(일간/주간/월간) 전체 합계**를 그대로 보여줌 — 페이지를 넘긴다고 총매출 숫자가 바뀌지 않음(달라지는 건 아래 상세 내역 표만).
- 일간/주간/월간 탭을 바꾸거나 화살표로 다른 날짜·기간으로 이동하면 페이지는 항상 1페이지(가장 최근 날짜)로 다시 시작함.
- "이미지 복사"로 캡쳐하면 지금 보고 있는 그 페이지(그 날짜) 하나만 이미지에 담김 — 즉 이제 월간 탭이어도 그날 매출 건수가 아무리 많아도 표 길이가 하루치만큼만 늘어나서 이미지가 예전만큼 길어지지 않음.

- Playwright로 검증: 월간 탭에서 9/3(14건)·9/2(2건)·9/1(1건) 가짜 데이터로 페이지가 정확히 3개로 나뉘는지, 각 페이지에 그 날짜 건수만큼만 행이 뜨는지, 마지막 페이지에서 다음 화살표가 비활성화되는지, 위쪽 총매출 카드는 페이지 이동과 무관하게 기간 전체 합계(17건)를 유지하는지, 다른 달로 이동하면 다시 1페이지로 리셋되는지 확인함.

## 새 기능: 지표 분석 페이지 (총 회원수 · 신규 등록률 · 재등록률 · 이탈률 · 객단가) (2026-09-04)

"우리 센터 총 인원수에서 재등록률, 신규 등록률, 이탈률 등 기준을 보고... 객단가와 총 고객수에 따라서 재등록 이벤트든, 신규 이벤트든, 이탈률 이벤트든 그런것들을 기획할 수 있는 페이지"를 만들어달라는 요청으로 신규 페이지 `metrics.html`(상단 메뉴 "지표 분석")을 추가함. 지점장 전용 페이지라 트레이너 계정에는 메뉴에서 안 보임(다른 지점장 전용 페이지와 동일하게 `auth.js`의 `applyRoleNav`에서 처리).

- **매출 보고와는 별개로, 이 페이지는 자체적인 월 단위 화살표 네비게이션(◀ 2026년 9월 ▶ / "이번 달")을 가지고 있음** — 매출 보고의 `reportRefDate`와는 독립적인 상태값이라, 매출 보고에서 어느 날짜를 보고 있든 지표 분석 페이지를 열면 항상 실제 오늘이 속한 달부터 보여줌. "다음" 화살표는 실제 오늘이 속한 달에서는 비활성화됨(미래 달은 아직 계산할 데이터가 없어서).
- **핵심 지표 5개**: 총 회원수, 신규 등록(수/비율), 재등록률, 이탈률, 객단가. 각 카드에 전월 대비 증감(%)과 최근 6개월 미니 추세선(스파크라인)을 같이 보여주고, 그 아래 "최근 6개월 추이" 표로 같은 숫자를 표로도 확인할 수 있게 함(그래프만 보고 정확한 숫자를 못 읽는 문제 방지).
- **총 회원수**: 그 달 말일 기준, 헬스이용권·그룹PT·개인PT(`membership_end_date`/`group_pt_end_date`/`pt_end_date`) 중 하나라도 만료되지 않은 회원 수(중복 제거). 락커·운동복만 있는 경우는 부가 서비스로 보고 총 회원수 계산에서 제외함. 참고로 `members.status` 컬럼은 실제로는 한 번도 `'active'` 말고 다른 값으로 바뀐 적이 없는 죽은 컬럼이라(`'expired'`/`'left'`로 세팅하는 곳이 코드 어디에도 없음), 활성 회원 여부는 이 컬럼이 아니라 만료일 컬럼들로 직접 판단함.
- **신규 등록**: 그 달 매출 중 "신규 회원권/PT/그룹PT"(`*_new` 카테고리) 매출을 낸 회원 수 ÷ 총 회원수.
- **재등록률 · 이탈률 — 대시보드의 "상품별 재등록 현황"과 분모가 다른 숫자임(중요)**: 대시보드의 기존 "상품별 재등록 현황"은 TM 상담을 실제로 진행한 회원만 분모로 잡는데, 이 페이지는 **그 달에 만료 "예정"이었던 모든 (회원, 카테고리) 건**을 분모로 잡음 — TM 콜을 아예 안 돌린 만료 회원도 그대로 분모에 남음. 지점장님과 상의해서 "TM 재등록률이 올라가면 만료 예정 인원 대비 실제 재등록 인원 비율도 올라갈 것"이라는 방향에 맞춰 이렇게 정함. 판정 방식: 만료일 기준 -14일~+30일 사이에 실제 재등록 매출이 있거나, 관련 TM 기록의 상태가 `renewed`(만료일 -60일~+30일 사이 상담)로 남아있으면 "재등록" — 둘 다 없이 만료 후 30일이 지나면 "이탈", 아직 30일이 안 지났으면 "집계중"(재등록률·이탈률 어느 쪽에도 안 잡히는 대기 상태, 표에는 "(집계중 N)"으로 같이 표시). 이번 달처럼 아직 30일이 안 지난 건이 많은 달은 재등록률이 낮게(때로는 0%로) 보일 수 있는데, 이건 실제로 재등록을 안 한 게 아니라 아직 판정 기간이 안 끝난 것뿐이라 추천 이벤트 문구에도 "집계중 N건은 제외"라고 같이 안내함.
- **객단가**: 그 달 총매출 ÷ 그 달에 실제 결제한 회원 수(중복 제거, `member_id` 기준).
- **📌 이번 달 추천 이벤트**: 위 5개 지표를 규칙 기반으로 판단해서 카드로 보여줌 — 총 회원수가 전월 대비 2% 넘게 줄면 "신규 회원 유치 이벤트"(빨강/긴급), 재등록률이 50% 미만이면 "재등록 유도 이벤트"(노랑/주의), 이탈률이 30% 이상이면 "이탈 방지·컴백 이벤트"(빨강/긴급), 객단가가 전월 대비 5% 넘게 떨어지면 "객단가를 높이는 이벤트"(노랑/주의). 넷 다 안 걸리면 "전반적으로 안정적이에요"라는 초록 카드 하나로 대체됨. 임계값은 `data.js`의 `METRICS_THRESHOLDS`에 상수로 빼뒀으니, 실제 운영해보고 너무 자주/안 뜬다 싶으면 숫자만 조정하면 됨.

## 지표 분석에 "상품(플랜)별 등록 현황" 추가 (2026-09-04)

"3개월권/6개월권/12개월권, PT 10·20·30·50·100회 이런 것도 등록률 조사가 필요해. 12개월권 기준으로 이벤트를 기획했으면 12개월 등록률이 높아야 하는데 그런 것도 확인해야 하니까"라는 요청으로, 지표 분석 페이지(`metrics.html`)에 카테고리 단위(헬스이용권/그룹PT/개인PT)보다 더 세분화된 "구체적 상품(플랜)" 단위 등록 현황 섹션을 추가함. 같은 요청에서 "9월부터는 바디코디에서 정산한 걸 내가 직접 앱에 다 기록 중이라 괜찮을 것 같다"고 하셔서 — 즉 엑셀 일괄 업로드 대신 매출 입력 화면에서 직접 상품을 골라 입력하는 방식으로 9월부터 전환하신다는 뜻이라, 아래 "상품 연결" 방식이 실제로 잘 작동하는지가 더 중요해짐.

- **어떻게 상품(플랜)을 구분하나**: 이용권 관리 화면에서 미리 등록해둔 상품 목록(`products` 테이블)에는 "헬스이용권 3개월/6개월/12개월"처럼 상품마다 `duration_days`(기간, 일 단위)나 `sessions`(PT 횟수)가 이미 구조화되어 저장돼 있음. 매출 입력 화면에서 매출을 등록할 때 이 상품 목록 중 하나를 직접 고르면 그 매출 건에 `product_id`가 남는데, 지표 분석 페이지는 이 `product_id`로 진짜 어떤 플랜이 팔렸는지 정확히 집계함 — "3개월/6개월/12개월"을 코드에 미리 못박아두지 않고, 실제 등록된 상품을 그대로 씀(나중에 상품을 새로 추가해도 자동으로 반영됨).
- **"상품 미연결" 항목 — 데이터 연동 점검용**: 매출 입력 시 상품을 안 고르고 직접 입력했거나(과거 습관), 상품 선택 기능이 없는 엑셀 일괄 업로드로 들어온 매출은 `product_id`가 비어있어서 어떤 구체적 플랜인지 알 수 없음. 이런 건들은 각 카테고리 표 맨 아래에 "상품 미연결(직접 입력 등)"으로 따로 모아서 건수/비중을 그대로 보여줌 — 이 숫자가 크면 "매출 입력할 때 상품을 안 고르고 있다"는 신호라서, 지점장님이 직접 매출 입력 습관을 점검하실 수 있게 했음. (Playwright로 상품 연결된 매출과 미연결 매출을 섞은 가짜 데이터를 넣어서, 연결된 건은 정확히 해당 상품에, 미연결 건은 "상품 미연결"에 정확히 집계되는지 확인함 — 자세한 내용은 아래 검증 항목 참고)
- **표시 내용**: 카테고리(헬스이용권/그룹PT/개인PT)별로 패널을 나누고, 각 패널 안에 플랜별 이번 달 건수·전체 대비 비중(%)·전월 대비 증감(건수 기준 %, 전월이 0건이면 "▲ 신규"로 표시)을 표로 보여줌. 플랜 정렬은 기간(일)/횟수 오름차순(1개월→3개월→6개월→12개월, 10회→20회→30회…)이라 자연스러운 순서로 읽힘. 이번 달 등록이 아예 없는 카테고리는 "이번 달 등록 없음"으로만 간단히 표시.
- 화면 상단의 월 화살표 네비게이션(◀ 2026년 9월 ▶)과 그대로 같이 움직임 — 다른 달로 이동하면 이 섹션도 그 달 기준으로 다시 계산됨.
- `data.js`의 `fetchMetricsRawData()`가 불러오는 매출 쿼리에 `product:products(id,name,category,duration_days,sessions)` 조인을 추가해서(선택 항목이라 상품이 연결 안 된 매출은 그냥 null로 옴) 추가 API 호출 없이 한 번에 다 가져옴. 실제 집계는 `computeProductPlanStats(monthStr, raw)` 순수 함수(`data.js`)에서 함.
- Playwright로 검증: 3개월권(8월 3건→9월 1건, 감소), 6개월권(8월 0건→9월 1건, "신규"), 12개월권(8월 1건→9월 1건, "전월과 동일") 세 가지 증감 패턴이 배지에 정확히 표시되는지, 상품 미연결 매출 2건이 "상품 미연결"로 따로 집계되는지, 그룹PT처럼 이번 달 등록이 없는 카테고리가 "이번 달 등록 없음"으로 깨지지 않고 뜨는지, 개인PT 10회/30회가 sessions 오름차순으로 정렬되는지 확인함.

## 새 기능: 미수금(분할 결제) 관리 (2026-09-04)

"PT 30회를 등록했는데, 이분이 우선 오늘 계약금 436,000원만 결제하고 다음에 오셔서 미납금 1,379,000원 결제한다고 하시게 되면, PT 30회 1,815,000원 정상가로 등록하고 결제금액을 436,000원만 하면 미수금 결제 처리로 되게, 그리고 다시 결제할 때 회원님 정보 들어가서 결제 가능하게 해달라. 미수금 처리 하기 전에 잔금 얼마 남았는지 알람으로 확인 가능하게"라는 요청으로 만든 기능.

**⚠️ 이 기능을 쓰려면 Supabase에 새 테이블을 하나 먼저 만들어야 함 — `migration_42_receivables.sql`을 Supabase SQL Editor에서 실행해주세요 (코드 배포와 별개로, 배포 전이든 후든 상관없이 한 번만 실행하면 됨). 이 SQL을 실행하기 전까지는 미수금 관련 기능(회원 등록 시 부분 결제, 잔금 받기 등)을 쓰면 오류가 남.**

- **핵심 동작**: 회원 등록(신규/기존 회원 이용권 판매 모두)할 때 상품마다 "정상가"와 "오늘 결제 금액" 두 칸이 나란히 있음. 상품을 고르면 둘 다 상품 가격으로 자동으로 채워지고(=오늘 전액 결제로 가정), 오늘 일부만 받았으면 "오늘 결제 금액" 칸만 실제로 받은 금액으로 고쳐 적으면 바로 아래에 "미수금 ○○원"이 자동으로 계산돼서 뜸(따로 체크박스를 누를 필요 없음). 이때:
  - 이용권/PT 등 상품 자체는 정상가 기준으로 **바로 전부 등록됨**(예: PT 30회면 잔여횟수 30회가 바로 채워짐, 이용권 만료일도 정상 기간대로 바로 잡힘) — 결제가 덜 됐다고 상품 등록이 미뤄지지 않음.
  - **매출(`sales`)에는 오늘 실제로 받은 금액만 남음**(정상가 전체가 아님) — 이 부분이 중요한데, 대시보드/지표 분석/매출 보고 등 기존 매출 관련 화면들은 전부 이 값을 그대로 씀. 그래야 "오늘 매출"이 실제로 오늘 받은 현금과 일치함.
  - 못 받은 나머지 금액(잔금)은 새로 만든 `receivables`(미수금) 테이블에 별도로 기록됨.
- **등록 전 확인 알람**: 잔금이 남는 항목이 하나라도 있으면, 등록 버튼을 눌렀을 때 바로 등록되지 않고 먼저 확인 팝업이 뜸 — "아래 항목에 잔금이 남아있어요. - 개인PT 30회: 잔금 1,379,000원 / 미수금으로 등록하고 진행하시겠습니까?" 여기서 취소하면 아무것도 등록되지 않고, 확인해야 실제로 등록됨(신규 회원 등록·기존 회원 이용권 판매 두 화면 모두 동일하게 적용).
- **잔금은 어디서 받나 — 회원 상세 화면**: 미수금이 남아있는 회원은 회원 목록에서 이름 앞에 주황색 점(●)이 표시됨(이름이 길어서 잘리는 칸이라, 배지 대신 항상 보이는 작은 점으로 표시함). 그 회원을 클릭해 상세 화면을 열면 상단에 "⚠️ 미수금" 섹션이 뜨는데, 여기서 상품명·잔금·지금까지 받은 금액이 보이고 "잔금 받기" 버튼이 있음. 눌러서 이번에 받을 금액(기본값은 남은 잔금 전액, 필요하면 또 일부만 받는 것도 가능)·결제 수단·날짜를 넣고 저장하면:
  - 그 금액만큼 **새 매출 건이 하나 더 생김**(잔금을 받은 그 날짜의 매출로 정확히 잡힘) — 기존 대시보드/지표 분석 등 어디에도 코드를 더 안 건드려도 자동으로 반영됨.
  - 미수금 테이블의 "받은 금액"이 올라가고, 잔금이 0원이 되면 그 미수금 건은 "처리 완료"로 바뀌면서 회원 상세에서 미수금 섹션이 사라짐(주황 점도 없어짐).
  - 이번에도 잔금 전액이 아니라 일부만 받으면("이번에 X만 받으면 Y가 계속 미수금으로 남아요") 한 번 더 확인 팝업이 뜸.
- **상세 설정에서도 조정 가능**: 기존 회원 이용권 판매(장바구니) 화면의 "상세설정" 팝업에도 "정상가(계약 금액)"와 "오늘 결제 금액" 두 칸이 따로 생겨서, 상품 목록에서 담을 때 말고 나중에 세부 조정할 때도 부분 결제로 바꿀 수 있음.
- (같은 날 UI 수정) 처음엔 회원 등록 화면에 "오늘 일부만 결제" 체크박스를 누르면 "오늘 결제 금액" 칸이 나타나는 방식으로 만들었는데, 지점장님이 실제 화면 캡처를 보내주시면서 "정가 입력칸, 현장 결제칸을 아예 따로 만들어서 현장 결제칸에 436,000 입력하면 미수금이 알아서 계산되게" 해달라고 요청하셔서 — 체크박스 없이 "정상가"·"오늘 결제 금액" 두 칸을 처음부터 항상 나란히 보여주고, 오늘 결제 금액을 정상가보다 적게 적으면 바로 아래에 미수금 안내가 뜨는 지금 방식으로 바꿈. (참고: 체크박스 방식일 때 회원 이름 칸이 좁아서 "오늘 결제 금액" 입력칸이 화면에 실제로는 안 나타나 보이는 표시 버그도 같이 있었는데, 이번 수정으로 자연히 해결됨)
- **데이터 구조**: 새 테이블 `receivables`(정상가/총액, 지금까지 받은 금액, 상태, 원래 계약금 매출 건과의 연결 등을 담음). `sales` 테이블은 전혀 안 바뀜 — 미수금 기능을 켜기 전과 마찬가지로 "그 매출 건에서 실제로 받은 금액"만 담는 원칙을 그대로 유지함.
- Playwright로 전체 시나리오를 실제로 재현해서 확인함: PT 30회(1,815,000원) 등록하면서 436,000원만 결제 → 확인 팝업 문구 정확히 뜨는지 → 회원은 즉시 30회 전부 등록되는지 → 매출은 436,000원만 잡히는지 → 미수금이 1,379,000원으로 정확히 기록되는지 → 회원 목록에 표시가 뜨는지 → 회원 상세에서 미수금 섹션이 정확한 금액으로 뜨는지 → "잔금 받기"로 1,379,000원을 마저 받으면 새 매출 건이 생기고 미수금이 "처리 완료"로 바뀌어 섹션이 사라지는지까지 전부 확인함(자바스크립트 오류 없음).

## 지표 분석 "객단가"를 FC(헬스이용권·그룹PT·락커·운동복) 기준으로만 계산하도록 수정 (2026-09-04)

"객단가 측정하는 건 FC만 볼 거야. PT는 아예 별도라서 그리고 금액 차이도 너무 크게 발생해서 — 헬스 이용권, 운동복, 락커, 올바른 운동 무제한 그룹PT 이렇게 해서 계산해서 객단가 다시 나오게끔 해달라"는 요청으로 수정함.

- **원래는 어땠나**: 그 달 전체 매출(개인PT 포함 전부) ÷ 그 달에 결제한 회원 수로 계산했음. 그런데 개인PT는 건당 77만원~550만원대로 이용권(11만원~40만원대)과 가격대가 워낙 달라서, PT 등록이 몰린 달은 객단가가 실제 이용권 판매 감각과 안 맞게 확 튀는 문제가 있었음.
- **지금은**: `data.js`에 `METRICS_ARPU_CATEGORIES = ['membership', 'group_pt', 'locker', 'clothes']`를 새로 두고, `computeMonthlyMetrics()`에서 객단가를 계산할 때 이 4개 카테고리(헬스이용권·그룹PT·락커·운동복) 매출만 골라서 "그 매출 총합 ÷ 그 매출을 낸 회원 수"로 계산함. 개인PT와 "기타"(양도비 등) 매출은 객단가 계산에서 완전히 빠짐 — 각 매출 건이 어느 카테고리인지는 이미 "상품(플랜)별 등록 현황" 기능에서 쓰던 `saleCategoryGroup()` 함수를 그대로 재사용해서 판단함(상품이 연결된 매출은 그 상품의 카테고리로, 상품 연결이 없는 매출은 `sales.category` 값 앞부분으로 대략 판단).
- 총 회원수·신규 등록률·재등록률·이탈률 등 다른 지표는 이번 수정과 무관하게 그대로임(원래도 이 지표들은 헬스이용권/그룹PT/개인PT를 각각 따로 다루고 있어서 손댈 필요가 없었음).
- 화면에 있는 "객단가" 라벨을 전부 "객단가 (FC)"로 바꿔서 이게 PT를 뺀 수치라는 걸 바로 알 수 있게 했고, 하단 "계산 방법" 설명과 "객단가 하락" 이벤트 추천 문구(추천 문구에서 "PT 연계" 표현은 이제 안 맞아서 "장기권 업그레이드·그룹PT 연계"로 바꿈)도 같이 고쳤음.
- 순수 함수(`computeMonthlyMetrics`)에 직접 가짜 매출 데이터(헬스이용권 264,000원·개인PT 1,815,000원·그룹PT 693,000원·락커 10,000원·운동복 10,000원·양도비 30,000원)를 넣고 계산해서, 개인PT(1,815,000원)와 양도비(30,000원)를 낸 회원은 매출·인원수 어느 쪽에서도 제외되고 나머지 4건(977,000원, 회원 3명 → 객단가 325,667원)만 정확히 집계되는지 확인함.

## "최근 매출 내역" 항목에 구체적인 상품명을 같이 표시 (2026-09-04)

"일일이용권 매출을 입력했는데(전에도 등록했던 회원이라) '회원권 재등록'이라고만 뜬다, '일일입장권(회원권 재등록)'처럼 무슨 상품인지 같이 보이게 해달라"는 요청으로 수정함.

- **문제였던 것**: 매출 입력 화면·대시보드의 "최근 매출 내역" 표는 그동안 "항목" 칸에 `sales.category` 라벨(신규 회원권/회원권 재등록/PT 재등록 등)만 보여줬음. 상품을 골라서 등록해도(예: 일일입장권, 12개월권 등) 그 구체적인 상품명은 화면에 안 나타나고 카테고리만 뭉뚱그려 보였음.
- **어떻게 고쳤나**: `data.js`에 `saleDisplayItemWithCategory(sale)` 함수를 새로 추가함 — 이미 있던 `saleDisplayItemName()`(상품이 연결돼 있으면 그 상품명, 없으면 엑셀 가져오기 메모에서 뽑은 이름, 그것도 없으면 카테고리 이름)으로 구체적인 이름을 구하고, 그 이름이 카테고리 이름과 다르면 "상품명(카테고리)" 형태로 합쳐서 보여줌(예: "일일입장권(회원권 재등록)", "일일입장권(신규 회원권)"). 구체적인 이름을 못 찾아서 결국 카테고리 이름 그대로인 경우는 괄호를 중복으로 안 붙이고 카테고리 이름만 보여줌(예: 상품 선택 없이 그냥 "회원권 재등록"으로만 직접 입력한 매출).
- 매출 입력 화면·대시보드가 공통으로 쓰는 `fetchRecentSales()` 쿼리에 `product:products(name)` 조인을 추가해서(원래는 상품명을 안 가져오고 있었음) 이 표시가 실제로 동작하게 함. 대시보드의 "매출 보고 이미지"(캡쳐/공유용)에 들어가는 매출 목록도 같은 캐시를 쓰기 때문에 자동으로 같이 적용됨.
- 다른 화면(센터 매출, 대시보드의 다른 상품별 표 등)에서 이미 상품명만 보여주고 있던 곳들은 그대로 두고, "카테고리만 보여주던" 세 곳(매출 입력 화면 표, 대시보드 최근 매출 내역 표, 매출 보고 이미지)만 이번에 고쳤음.
- Playwright로 확인: 일일입장권 재등록 건은 "일일입장권(회원권 재등록)"으로, 신규 건은 "일일입장권(신규 회원권)"으로, 상품 연결이 없는 건은 그냥 "신규 회원권"으로(괄호 중복 없이) 정확히 표시되는 걸 확인함(자바스크립트 오류 없음).

## 매출 입력 화면 - 등록할 때마다 날짜가 오늘로 되돌아가던 문제 수정 (2026-09-04)

"매출 날짜를 9/3으로 등록해도 9/4로 잡힌다"는 문의로 확인함.

- **원인**: 매출을 하나 등록하고 나면 폼이 초기화되면서 "날짜" 칸이 항상 오늘 날짜로 강제로 리셋되고 있었음. 어제(9/3) 날짜로 여러 명(예: 일일입장권 손님 여러 명)을 몰아서 입력할 때, 첫 명은 날짜를 9/3으로 바꿔서 잘 등록해도, 등록 버튼을 누르는 순간 날짜 칸이 오늘(9/4)로 되돌아가버려서 — 두 번째 손님부터는 날짜를 매번 다시 9/3으로 바꿔주지 않으면 그대로 오늘 날짜로 잘못 등록되는 문제였음(직접 9/3으로 등록해도 "이번 건"은 맞게 들어가지만, 그다음 등록부터 자꾸 오늘로 돌아가 있었던 것).
- **어떻게 고쳤나**: 등록 후에도 날짜 칸은 방금 쓴 값을 그대로 유지하도록(오늘 날짜로 강제로 안 돌아가게) 바꿈. 담당자·결제수단 등 나머지 칸은 기존처럼 초기화되고, 시각 칸은 여전히 실제 등록 시점의 현재 시각으로 채워짐 — 날짜 칸만 "마지막으로 쓴 날짜"를 계속 기억함. 이제 어제 날짜로 여러 명을 몰아서 등록할 때, 맨 처음 한 번만 날짜를 바꿔주면 그다음부터는 계속 그 날짜가 유지돼요.
- Playwright로 확인: 날짜를 9/3으로 바꿔서 첫 번째 손님을 등록한 뒤, 날짜 칸을 다시 안 건드리고 두 번째 손님을 등록해도 두 건 모두 9/3으로 정확히 저장되는 걸 확인함(전에는 두 번째 건이 9/4로 잘못 들어갔을 상황).
- 참고: "미팅 기록"(meetings.html) 화면의 날짜 칸도 등록할 때마다 오늘 날짜로 되돌아가는 같은 패턴이 있는데, 이번에는 매출 입력 화면만 고쳤음. 미팅 기록도 같은 방식으로 여러 건을 몰아서 입력하는 경우가 있으시면 말씀해주시면 같이 고쳐드릴게요.

## 다크 모드(블랙&화이트) 토글 추가 (2026-09-04)

"디자인을 블랙&화이트 이런 식으로 전환 가능하도록 해달라"는 요청으로 추가함. AskUserQuestion으로 두 가지를 먼저 확인함: ① 색을 다 빼는 무채색 모드가 아니라 배경은 검정·글자는 흰색으로 바뀌되 상태색(재등록률 상승/하락, 미수금 경고색 등)은 그대로 유지하는 **다크 모드**, ② 화면을 통째로 바꾸는 게 아니라 **화면 우측 상단에 전환 버튼**을 둬서 사용자가 원할 때 켜고 끌 수 있게.

- **어떻게 켜고 끄나**: 로그인이 필요한 모든 화면(대시보드, 회원 관리 등 14개 화면) 우측 상단, "로그인 정보" 뱃지 바로 왼쪽에 "🌙 다크"/"☀️ 라이트" 버튼이 자동으로 뜸. 누르면 즉시 전환되고, 어떤 화면으로 이동하든 로그아웃하기 전까지 계속 유지됨(브라우저에 저장 - `localStorage`의 `gymops_theme` 값, 같은 브라우저에서만 유지되고 다른 기기/브라우저에는 안 옮겨감).
- **버튼은 어떻게 자동으로 생기나**: 화면마다 버튼 마크업을 일일이 추가하는 대신, 로그인된 화면이라면 공통으로 불러오는 `auth.js`에 버튼을 자동으로 삽입하는 코드를 한 번만 추가함 — 모든 화면에 똑같이 있는 "로그인 정보" 표시 칸(`id="roleBadge"`)을 기준점 삼아 그 옆에 버튼을 끼워 넣는 방식이라, html 파일들을 따로 고칠 필요가 없었음. 로그인이 필요 없는 "공유된 매출 보고" 페이지(`report.html`)는 이 버튼이 안 뜸(원래 로그인 없이 보는 화면이라 자연스러움).
- **깜빡임(전환 전 잠깐 밝은 화면이 보였다 어두워지는 현상) 방지**: 18개 화면 전부의 `<head>` 맨 위쪽(스타일시트를 불러오기도 전)에 아주 작은 스크립트를 심어서, 저장된 값이 "다크"면 화면을 그리기 전에 미리 다크 모드를 적용해둠. 그래서 다크 모드로 켜둔 상태에서 새로고침하거나 다른 화면으로 넘어가도 밝은 화면이 잠깐이라도 번쩍이지 않음.
- **색은 어떻게 정했나(`style.css`)**: 기존에 쓰던 색상 변수(`--indigo-600`, `--slate-50`~`--slate-900` 등)를 `<html data-theme="dark">`가 붙으면 어두운 색 계열로 바꿔치기하는 방식이라, 카드·표·버튼·입력칸·모달 등 화면 대부분이 이 변수들만 그대로 쓰고 있어서 별도로 손 안 대도 자동으로 다크 모드가 적용됨. 다만 "바탕면 색"(카드/표/모달 배경 등)과 "색깔 있는 배경 위의 흰 글씨"(버튼·뱃지·히어로 카드 등)가 원래 똑같이 `--white` 변수 하나를 같이 쓰고 있어서, 그대로 다크 모드를 적용하면 버튼 글씨까지 어두워져 버리는 문제가 있었음 — 그래서 "바탕면" 전용 `--surface` 변수를 새로 만들어 분리함(라이트 모드에서는 `--surface`가 그냥 흰색이라 기존 화면과 완전히 동일하게 보이고, 다크 모드에서만 어두운 값으로 바뀜).
- **일부러 색을 안 바꾼 것들**: 재등록률/이탈률 배지의 빨강·초록, 미수금 경고 노란색, 히어로 카드의 파랑/보라/초록 그라데이션, 확률 단계별 행 배경색(노랑/주황/초록 등) 같은 "의미를 담은" 작은 색상 요소들은 그대로 뒀음 — 다크 모드라고 색 자체를 다 빼버리면 오히려 한눈에 상태를 구분하기 어려워지기 때문에, 어두운 배경 위에 밝은 색 칩으로 그대로 떠 있게 남겨둠(무채색 모드가 아니라 다크 모드로 결정한 이유).
- 입력칸/셀렉트/텍스트영역처럼 화면마다 배경색을 따로 안 정해줘서 브라우저 기본값(흰 배경)에 의존하던 곳들이 많아서, 다크 모드에서도 흰 박스로 남지 않도록 전체에 한 번에 적용되는 공용 규칙을 추가함. 날짜/시각 입력칸의 달력·시계 아이콘(브라우저가 그리는 고정 어두운색)도 다크 모드에서 안 보이는 문제가 있어서 색을 뒤집어줌.
- Playwright로 확인: 홈 화면·회원 관리 화면(표+상세 모달 포함)에서 토글 버튼 클릭 시 즉시 다크 모드로 전환되고, 새로고침해도 유지되며, 자바스크립트 오류 없이 정상 동작하는 걸 스크린샷으로 확인함.
- DB 변경은 없음(순수 CSS/JS + 브라우저 저장소만 사용) — 이번 배포는 SQL 실행 없이 파일만 올리면 됨.

## 다크 모드 색상 테마를 "크림슨 글로우 다크"로 교체 (2026-09-04)

"디자인 자체도 수정 가능한지" 물어보셔서, 대시보드 화면을 기준으로 서로 다른 스타일 10가지 시안을 캔버스로 만들어서 먼저 보여드림 → "약간 붉은색 계열로 3가지" 요청 → 그중에서 붉은색 계열만 남겨서 "블랙&레드로 3가지"로 다시 추려서 보여드림 → 그중 **"크림슨 글로우 다크"**를 골라주셔서, 실제 화면(`style.css`)에 적용함.

- **무엇이 바뀌었나**: 위에서 만든 다크 모드(토글 버튼으로 켜고 끄는 방식)는 그대로 두고, 다크 모드를 켰을 때의 "색상 테마"만 기존 인디고/슬레이트 계열에서 검정에 가까운 배경 + 크림슨(진한 빨강) 포인트색으로 교체함. 라이트 모드(기본 화면)는 전혀 손 안 댐 — 토글 버튼으로 다크 모드를 켰을 때만 이 새 테마가 보임.
- **구체적으로**: `style.css`의 `:root[data-theme="dark"]` 블록 안 색상 값들을 다 크림슨 톤으로 바꿈 — 브랜드 포인트색(`--indigo-600`/`--indigo-700`, 버튼·활성 메뉴·포커스링·강조 텍스트 등에 쓰임)을 크림슨 레드로, 배경/바탕면 색을 좀 더 검정에 가깝게, 테두리색을 옅은 반투명 빨강으로 바꿈. 다크 모드에서만 IBM Plex Sans KR 폰트를 쓰도록 구글 폰트를 불러왔고(라이트 모드는 기존 폰트 그대로), 화면 우측 상단에 은은하게 번지는 붉은 원형 그라데이션("글로우")을 배경 장식으로 추가하고, "+ 회원 등록" 같은 주요 버튼에는 붉은 그림자(글로우)를 줘서 포인트색이 더 도드라지게 함.
- **뱃지 색상 충돌 버그를 미리 잡음**: "재등록 예정"/"OT 예정" 상태에 쓰이는 `badge-blue`가 원래 브랜드 포인트색 변수(`--indigo-700`)를 그대로 같이 쓰고 있어서, 포인트색을 빨강으로 바꾸면 이 뱃지까지 같이 빨개져서 "파란 뱃지"라는 이름과 의미가 깨지는 문제가 있었음 — `--blue-600`이라는 전용 변수를 새로 만들어서 분리해뒀기 때문에, 이 뱃지는 다크 모드에서도 원래 파란 느낌을 그대로 유지함.
- **위험/경고색도 다시 구분함**: 에러 문구·미수금 등에 쓰이는 `--red-600`(위험색)이 브랜드 포인트색과 똑같이 빨간색이라 헷갈릴 수 있어서, 다크 모드에서는 `--red-600`을 더 밝은 연분홍 계열로 따로 잡아서 "이건 브랜드색이 아니라 경고/위험 표시다"가 한눈에 구분되게 함.
- **재등록률·미수금 경고·히어로 카드 그라데이션 등 "의미를 담은" 색상은 이전과 동일하게 그대로 둠** — 이번에도 색을 다 빼는 게 아니라 톤을 바꾸는 작업이라, 그 원칙은 유지함. 다만 상단 메뉴 활성 탭 배경, 홈 화면 타일 아이콘 배경처럼 원래 옅은 인디고색(`#eef2ff`)을 하드코딩해 둔 몇몇 곳은 포인트색이 안 따라와서 다크 모드 전용으로 옅은 빨강 배경을 따로 맞춰줌.
- Playwright로 확인: 홈 화면·회원 관리 화면(표+상세 모달 포함)에서 다크 모드가 검정 배경+크림슨 포인트색+우상단 글로우로 정상적으로 보이고, 상태 뱃지(초록/노랑/분홍)는 원래 의미대로 그대로 유지되며, 자바스크립트 오류 없이 동작하는 걸 스크린샷으로 확인함.
- DB 변경 없음(CSS만 수정) — 배포 시 SQL 실행 불필요.

### 뒤이어 발견/수정: 뱃지 글자가 배경색과 겹쳐서 잘 안 보이던 문제 (2026-09-04)

크림슨 글로우 다크를 적용한 화면 스크린샷을 보시고 "이런거 색상 배치가 잘 안 맞는 거 같은데, 글씨도 잘 보이게끔 다시 디자인해줄 수 있냐"고 피드백 주셔서 확인함(회원 목록의 만료일 D-day 뱃지 - 초록/빨강 알약 모양 - 글자가 배경색과 거의 비슷해서 잘 안 보이는 문제였음).

- **원인**: `badge-green`/`badge-red`(D-day 뱃지, "만료 D+3" 등)처럼 배경은 항상 연한 색으로 고정해두고 글자색만 `var(--green-600)`/`var(--red-600))` 같은 다크모드 변수를 쓰던 곳들이 있었음. 이 변수들은 원래 "어두운 배경 위에 놓이는 일반 텍스트"용으로 다크 모드에서 더 밝은 색(연두·연분홍)으로 바뀌게 만들어뒀는데, 정작 이 뱃지들은 배경 자체가 항상 연한 색(다크 모드에서도 안 바뀜)이라서, 그 위에 놓이는 글자까지 밝아지면 배경과 글자가 둘 다 밝은 색이라 거의 안 보이게 됐던 것.
- **어떻게 고쳤나**: `badge-green`/`badge-red`/`badge-blue`, `error-text`/`success-text`, 완료 알림(`toast`/`toast-danger`), `지표 분석` 화면의 추천 카드(`rec-critical`/`rec-good`), `PT 관리` 화면의 O/X 토글(`toggle-ox`) 등 "배경은 고정, 글자색만 변수"였던 곳들을 전부 찾아서, 라이트 모드일 때 원래 보이던 진한 색(진한 초록 `#16a34a`, 진한 빨강 `#dc2626` 등)으로 고정값으로 박아둠 — `badge-amber`/`badge-orange`처럼 원래부터 잘 되어있던 뱃지들과 똑같은 방식으로 맞춘 것. 이러면 라이트/다크 모드 상관없이 항상 똑같이 잘 보임. 반대로 센터 매출 화면의 "FC 목표 저장" 실패 메시지처럼 카드 배경 위에 바로 놓이는 일반 텍스트인데 거꾸로 색이 고정되어 있던 곳은, 다크 모드에서 어두운 배경과 겹쳐 안 보이지 않도록 반대로 변수를 쓰도록 고침.
- Playwright로 회원 목록 표를 확대 캡처해서, D-88/D-58/D-27(초록)과 "만료 D+3"(빨강) 뱃지 글자가 이제 배경과 뚜렷하게 대비되어 잘 보이는 걸 확인함.
- DB 변경 없음(CSS만 수정) — 배포 시 SQL 실행 불필요.

## 다크 모드 색상 테마를 "미디엄 다크그레이 레드"로 재교체 (2026-09-05)

"크림슨 글로우 다크"를 실제로 밤에 써보시고 "눈이 별로 안 좋아서 디자인이 너무 어둡다"는 피드백을 주심 — 그레이&레드 또는 밝은 레드 톤으로 5가지 시안을 새로 만들어 보여드림 → "흰색 계열은 밤에 보면 또 밝다, 너무 다크하지도 않으면서 좀 많이 밝은 다크그레이 + 빨간 계열"로 다시 구체화해주셔서, 어둡기 정도가 다른 3가지("딥"/"표준"/"라이트")를 다시 캔버스로 보여드림 → 그중 가장 어두운 **"미디엄 다크그레이 레드 (딥)"**을 골라주셔서, 실제 화면(`style.css`)에 적용함. 크림슨 글로우 다크는 이번 교체로 완전히 대체됨.

- **무엇이 바뀌었나**: 다크 모드를 켰을 때의 배경이 거의 검정에 가까웠던 것을, 눈이 편한 중간 톤 진회색(page 배경 `#2b2b2f`, 카드/표/모달 등 바탕면은 그보다 살짝 밝은 `#35353a`)으로 바꿈. 포인트색은 계속 크림슨 레드(`#dc2626`)로 유지 — 버튼·활성 메뉴·포커스링 등은 색 자체는 그대로이고 배경 밝기만 바뀐 셈. 크림슨 글로우 다크에서 추가했던 우측 상단 그라데이션 "글로우" 장식과 버튼 그림자(글로우) 효과, 다크 모드 전용 IBM Plex Sans KR 폰트는 전부 제거해서, 순정 Noto Sans KR 폰트에 은은한 그림자만 있는 차분하고 플랫한 느낌으로 되돌림. 라이트 모드(기본 화면)는 이번에도 전혀 손 안 댐.
- **배경 밝기 단계 구성**: 페이지 배경(`--slate-50`) < 카드/표/모달 등 바탕면(`--surface`) < 입력칸 살짝 눌린 톤(`--slate-100`) 순으로 밝기를 나눠서, 카드가 페이지 위에 "떠 있는 패널"처럼 보이게 함 — 크림슨 글로우 다크 때는 페이지와 카드가 똑같은 색(`--surface`)을 같이 썼던 것과 달리, 이번엔 톤을 살짝 분리함.
- 상단 메뉴 활성 탭/홈 화면 타일 아이콘 배경, 입력칸 포커스 링, 날짜·시간 선택 아이콘 색 반전 등 기존에 크림슨 값(`rgba(220,38,38,...)`)으로 따로 맞춰뒀던 하드코딩 오버라이드들은 포인트색 자체가 안 바뀌었으므로 그대로 유지함.
- `--blue-600`(재등록/OT 예정 뱃지 전용 파란색)과 지난번에 고친 뱃지·에러문구·완료 알림 등의 글자색 하드코딩(배경은 고정, 글자색도 고정이라 테마와 무관하게 항상 잘 보임)은 이번 배경 밝기 변경과 무관하게 그대로 유지됨 — Playwright로 회원 목록 표를 다시 확인해서 D-day 뱃지(초록/빨강)가 새 배경에서도 여전히 뚜렷하게 잘 보이는 걸 확인함.
- Playwright로 홈 화면·회원 관리 화면을 다크 모드로 캡처해서, 중간 톤 진회색 배경 위에 카드가 살짝 밝은 패널로 떠 보이고, 크림슨 포인트색과 뱃지 색상은 전과 다름없이 잘 보이며, 글로우/그림자 효과 없이 플랫한 느낌으로 바뀐 것과 자바스크립트 오류 없이 정상 동작하는 걸 확인함.
- DB 변경 없음(CSS만 수정) — 배포 시 SQL 실행 불필요.

## 배포 방법 (GitHub 웹 업로드 → Vercel 자동 배포)

**2026-09-03에 실제로 확인된 올바른 방법** — 예전엔 "Vercel에 zip을 드래그 앤 드롭"으로 잘못 적혀 있었는데, 실제로는 Vercel 프로젝트가 GitHub 저장소(gym-ops)와 연동되어 있어서 **zip 자체가 아니라 압축을 푼 개별 파일들을 GitHub 저장소 페이지에 웹으로 업로드**해야 함 (GitHub은 zip 파일을 자동으로 안 풀어줘서, zip 파일 자체를 드래그하면 업로드 오류가 남 — 실제로 이 문제가 발생했었음).

1. **zip으로 묶기 전에, 모든 HTML의 `config.js`/`auth.js`/`data.js`/`style.css` 뒤에 붙은 `?v=(숫자)` 캐시 버전을 새 숫자로 바꿔야 함**(예: `date +%s`로 나온 값으로 전체 치환) — 안 바꾸면 브라우저가 옛날 자바스크립트를 계속 캐싱해서 코드를 고쳐도 화면에 반영이 안 될 수 있음("배포 후 옛날 자바스크립트가 캐싱되는 문제 수정" 항목 참고)
2. 이 폴더 전체를 zip으로 압축해서 사용자에게 전달
3. **사용자는 이 zip을 자기 컴퓨터에서 압축을 풀어야 함**(더블클릭 또는 우클릭 → 압축 풀기) — 그러면 `gym-ops` 폴더 안에 `dashboard.html`, `data.js` 등 개별 파일들이 생김
4. GitHub(github.com) 로그인 → `gym-ops` 저장소 → 저장소 루트 화면에서 "Add file" → "Upload files"(또는 이미 업로드 화면이 떠 있다면 그 화면) 진입
5. 압축 푼 폴더 안의 **파일들을 전부 선택**(zip 파일 말고, 그 안의 개별 파일들 — 폴더째로 드래그해도 브라우저가 지원하면 됨)해서 "Drag additional files here" 영역에 드래그 앤 드롭
6. 업로드 다 끝나면 아래로 스크롤 → "Commit changes" 부분에서 "Commit directly to the `main` branch"가 선택된 채로 커밋 버튼 클릭
7. main 브랜치가 바뀌면 Vercel이 자동으로 새로 배포함(수동으로 Vercel 쪽에서 따로 뭘 누를 필요 없음) — Vercel 프로젝트 페이지에서 "Deployments" 탭을 보면 새 배포가 뜨는 걸 확인할 수 있음
8. DB 스키마가 바뀌는 변경이면 코드 배포와 별개로 Supabase SQL Editor에서 해당 migration_*.sql을 먼저(또는 같이) 실행해야 함

- UI/UX 참고 기준으로 "비플(다른 헬스장 관리 프로그램)" 화면을 자주 캡처해서 보여주고 비슷하게 구현해달라고 요청하는 편

- 변경할 때마다: 코드 수정 → `node --check`로 문법 확인 → 로컬 정적서버(`python3 -m http.server`)+Playwright로 스크린샷 검증 → git commit → zip 재생성 → SendUserFile로 zip과 관련 migration_*.sql, 스크린샷을 함께 전달 → 사용자가 zip 압축을 풀어서 그 안의 개별 파일들을 GitHub 저장소(gym-ops)에 웹으로 업로드·커밋 (zip 파일 자체를 올리면 안 됨 — GitHub이 압축을 안 풀어줘서 업로드 오류가 남) → Vercel이 자동 배포 + (스키마 변경 있으면) Supabase SQL Editor에서 SQL 실행

## 새 세션에서 이어받을 때 체크리스트

1. 이 README와 `schema.sql` + `migration_*.sql` 전부를 읽고 현재 DB 구조를 파악
2. 각 html 파일의 `<script>`를 읽고 현재 UI/기능 상태 파악 (특히 `data.js`가 공용 함수 허브)
3. 사용자에게 "지금까지 안내드린 migration 파일들을 전부 Supabase에서 실행하셨는지" 확인
4. 이후 작업은 기존 코드 스타일(주석은 한국어로 "왜 이렇게 했는지" 설명 포함, 커밋 메시지도 한국어)을 그대로 따라가면 됨
